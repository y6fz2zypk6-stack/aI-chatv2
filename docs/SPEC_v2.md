## 1. 設計原則

### 1.1 二つの柱

**① 小説品質の出力を、チャットUIで読ませる。**
モデルには話者ラベル付きのプレーンテキストを書かせ、アプリ側で発話単位に分解して吹き出しにする。
JSONで返させない。構造化を強いると文体が痩せるため。

**② 世界の状態はアプリが持ち、モデルには持たせない。**
時刻・場所・在席者・天候・進行フラグはDBが正とする。モデルは「差分」だけを申告し、
検証と適用はアプリが行う。モデルの記憶に依存する設計を禁止する。

### 1.2 派生する規則

| 規則 | 理由 |
|---|---|
| 時刻の演算は `domain/calendar.ts` にのみ書く | 換算の重複実装は必ずズレる |
| 会話の順序は `messages.seq` が正。ULIDの時系列性に依存しない | 同一ミリ秒の連投で順序が壊れる |
| 再生成の基準ステートは「直前メッセージの `state_after`」 | `chats.state` を基準にすると時間が累積する |
| 参照に使うIDは作成後に変更しない（場所ID・エリアID・進行フラグのキー） | 参照が入れ子JSONにも入るため、リネームは黙って壊れる |
| 失敗は握り潰さず、警告として利用者に返す | 「静かに効かない」が最も直しにくい |

### 1.3 スコープ外

多人数同時利用・ロール権限・課金・モバイルネイティブアプリ・全文検索。
単一利用者・単一VPS・SQLite1ファイルの範囲に閉じる。

## 2. 構成と運用

### 2.1 リポジトリ

npm workspaces のモノレポ。ルート `package.json` に `"type": "module"` を置く
（`shared/` の tsc 出力をESMにするため。これが無いとサーバ起動時に named export が解決できない）。

```
shared/types.ts     API境界の型と共有定数（クライアント・サーバの両方から参照）
server/             Express 5 + better-sqlite3
  src/db/           スキーマ・マイグレーション・リポジトリ層
  src/domain/       純粋なドメインロジック（暦・ステート・ロア・イベント・進行フラグ・要約・記憶）
  src/llm/          OpenRouter・プロンプト組み立て・応答パース
  src/routes/       HTTPルート
  test/             回帰テスト（モックLLM + 実HTTP）
client/             React 18 + Vite + Zustand + React Router
docs/               SPEC・GUIDE
```

**層の依存方向は `routes → domain → db` の一方向**とする。`domain/` からHTTPを触らない。

### 2.2 実行

```bash
npm install
cp .env.example .env
npm run dev     # server:3000（API） / client:5173（Vite、/api をプロキシ）
npm run build && npm start   # 本番。Expressが client/dist を配信する
npm test        # .env基準の検証 → マイグレーション検証 → BIND検証 → 機能テスト
```

**`.env` と相対 `DB_PATH` はリポジトリルート基準**（`server/src/env.ts`）。
cwd は使わない。ルートの npm script は `-w server` 付きで走るため cwd が `server/` になり、
`dotenv/config` のままだと `server/.env` が読まれてルートの `.env` が無視される。
`server/.env` を置いても読まれず、起動時に注意が出る。
`server/data/` に旧いDBが残っている状態では**起動を中止する**（空DBに初期データを入れて
既存の会話が消えたように見えるのを防ぐ）。

### 2.3 環境変数

| 変数 | 既定 | 説明 |
|---|---|---|
| `OPENROUTER_API_KEY` | — | 必須。**ブラウザには渡さない** |
| `APP_PASSWORD` | 空 | 空だと認証が素通り。**公開VPSでは必須** |
| `SESSION_SECRET` | `APP_PASSWORD` | ログインパスワードを定数時間比較するためのHMAC鍵。セッションIDの署名には使わない |
| `DEFAULT_MODEL` | `anthropic/claude-opus-5` | |
| `UTILITY_MODEL` | `anthropic/claude-sonnet-5` | 要約・抽出・継続判定 |
| `PORT` / `DB_PATH` / `APP_URL` / `APP_TITLE` | 3000 / `./data/app.sqlite` / … | |
| `BIND` | 未設定 | 待ち受けるインターフェース。未設定なら全インターフェース。到達範囲を絞ったと見なすのはループバックと `100.64.0.0/10` のみ（§16.2） |
| `COOKIE_SECURE` | 未設定 | 未設定なら `APP_URL` が https のときだけ有効 |
| `TRUST_PROXY` | 未設定 | リバースプロキシ配下の段数（nginx背後なら `1`） |
| `ALLOW_UNAUTHENTICATED` | 未設定 | `1` のときだけ、無認証＋全インターフェースでの起動を許す |
| `OPENROUTER_BASE_URL` | OpenRouter | テストでモックに差し替えるための seam |
| `STREAM_CONNECT_TIMEOUT_MS` / `STREAM_IDLE_TIMEOUT_MS` | 60000 / 60000 | ストリームの待ち時間の上限（§5.7） |
| `IMAGE_TIMEOUT_MS` | 120000 | 画像生成の待ち時間の上限（§21.6） |

### 2.4 バックアップ

**DBは1ファイル（SQLite）で完結させる。** アバター画像も外部ファイルにせず、
320px WebP の data URL として `characters.avatar` / `personas.avatar` に埋める（1枚 2〜3KB）。
`DB_PATH` のファイル（既定 `<リポジトリルート>/data/app.sqlite`）をコピーすれば全データが揃うことを保つ。

スナップショット（§21）を使うと画像もこのファイルに入るので、**DBは目に見えて育つ**。
1枚あたり数百KB〜数MB。増えすぎたら会話画面から個別に削除する。

**コピー・移動は `-wal` / `-shm` も一緒に。** WALモードで動かしているので、
本体だけを持ち出すと直近の書き込みが欠ける。別のDBの `-wal` が隣に残っていると壊れる。
サーバを止めてから、3つまとめて扱うこと。

**起動時に開いたDBを1行で出す**（`[db] 使用中: <パス>（世界n / チャットn / メッセージn）`）。
DBを取り違えても画面は正常に動いてしまう（空の状態から始まるだけ）ので、
これが無いと「データが消えた」としか見えない。

## 3. データモデル

実装: `server/src/db/schema.sql` / `shared/types.ts`

### 3.1 テーブル

| テーブル | 役割 | 主な制約 |
|---|---|---|
| `worlds` | 世界。`areas`・`vars_schema` をJSONで持つ | |
| `characters` | キャラ。`is_npc_pool` で準レギュラー | `world_id` CASCADE |
| `personas` | ユーザーの分身。世界に属さない | |
| `scenarios` | 開始条件のテンプレート | `world_id` CASCADE |
| `chats` | 会話。`state` / `initial_state` を持つ | `scenario_id` は SET NULL |
| `messages` | 発言。`seq` が順序の正 | **UNIQUE(chat_id, seq)** |
| `message_variants` | 再生成の候補 | **UNIQUE(message_id, "index")** |
| `lorebook_entries` | 世界設定の断片 | |
| `locations` | 場所。IDはグローバル一意 | |
| `calendars` | 世界ごとの暦・天候表 | `world_id` が主キー |
| `world_events` | 条件付きイベント | `"when"` `"check"` は予約語 |
| `event_fires` | 発火履歴（チャット単位） | |
| `summaries` | あらすじ。`up_to_seq` が範囲の正 | |
| `memories` | キャラの長期記憶 | |
| `settings` | key-value | |
| `schema_migrations` | 適用済みマイグレーション | |

`PRAGMA foreign_keys = ON` は接続ごとにアプリ側で有効化する（SQLiteの既定はOFF）。

### 3.2 JSON列の扱い

`aliases` / `keys` / `participant_ids` / `state` / `state_after` / `areas` / `vars_schema` /
`"when"` / `set_vars` などはJSON文字列で保存し、**リポジトリ層で必ず展開してからAPI境界へ出す**。
ルートやドメインが生のJSON文字列を扱うことを禁止する。

### 3.3 `seq`

`messages.seq` はチャット内の1始まりの連番。以下すべての基準になる。

- 履歴窓の切り出し・前後メッセージの取得
- 未要約範囲（`summaries.up_to_seq`）・未抽出範囲（`chats.extracted_up_to_seq`）
- fork のコピー範囲（`seq <= 分岐点`）
- 削除時の巻き戻し範囲

**境界をメッセージIDで持たない。** 境界のメッセージが削除されると範囲が壊れるため、
`up_to_message_id` は表示・参照用に残しつつ、判定は必ず `seq` で行う。

### 3.4 継承フラグ

`events_enabled` / `vars_enabled` は `chats` → `scenarios` → `settings` の3段で解決する。
`chats` と `scenarios` の列は **NULL許容**で、NULLが「上位から継承」を意味する。

**解決結果と根拠を必ずUIへ返す。** `GET /chats/:id` は `flags` を返し、
`{ enabled, from: 'chat' | 'scenario' | 'settings' }` の形で「いまONかOFFか」「どこで決まったか」を示す。
「継承」とだけ表示すると結果が読めず、全体設定と会話ごとの設定が食い違っていることに気付けない。

```ts
resolveFlag(chat.events_enabled, scenario.events_enabled, settings.events_enabled)
// 先に見つかった非NULLを採用。どちらもNULLなら全体設定
```

### 3.5 会話の名前

`chats.title` は**利用者が付けたときだけ**入る。以前は最初のユーザー発言の
先頭24文字を自動で入れていたが、「つづけて」のような文字列が名前として残り続けるだけで、
home はそれを無視してキャラ名を出していた（＝付けた名前が表示されない）。

- 自動命名は**しない**。マイグレーション9で、最初の発言の先頭24文字と
  完全に一致する既存タイトルだけを空にした（自分で付けた名前は残る）
- 表示名の決め方は `chatDisplayName(title, characterName)`（`shared/types.ts`）に1つだけ置く。
  **付けた名前 → 先頭の参加キャラの名前 → `(無題の会話)`**。
  home・チャット画面・アルバムで呼び名がずれると同じ会話だと分からなくなる
- アルバムのAPIは**サーバ側で表示名まで解決して返す**（クライアントで再実装しない）
- 分岐は、元が無名なら分岐先も無名。「無題（分岐）」という名前が残らないように

## 4. ステート機構

実装: `server/src/domain/state.ts`

### 4.1 `ChatState`

```ts
{
  time: number;              // 暦元期からの通算分（整数）。これが時刻の唯一の内部表現
  location: string;          // 場所ID
  location_note: string;     // 未登録地の退避先。空でないとき location は据え置き
  weather: string;
  present: string[];         // 在席者のキャラID
  vars?: Record<string, VarValue>;  // 進行フラグ
}
```

### 4.2 差分の適用

モデルは `@@@STATE` フェンスで差分だけを返す。適用規則は以下。

| 項目 | 規則 |
|---|---|
| `elapsed_minutes` | `parseDurationMinutes` で読む。負値は0。1440超はそのまま適用し**警告**を返す（UIが「⚠ +Xh」を出す）。読めない値は既定の10分で進めて警告 |
| `location` | ID一致 → 表示名一致 → どちらも無ければ `location_note` に退避し警告 |
| `present_add` / `present_remove` | ID → 名前 → 別名 の順に解決。解決できなければ無視して警告 |
| `set_var` | スキーマ検証を通す（§8） |
| 天候 | **`weather_rollover_min`（既定 4:00）をまたいだときだけ**抽選する。日付の変わり目とは別の境界（§12.3） |

`present` は `(present ∪ add) − remove`。**場所が変わっても在席者は維持する**
（「二人で店を出る」が最頻のため。別れる場合はモデルが `present_remove` を明示する）。

#### 参加キャラと準レギュラー

キャラ定義がプロンプトに載る経路は2つだけで、履歴の内容もイベントの発火も関与しない。

| 経路 | 条件 |
|---|---|
| 参加キャラ（`chat.participant_ids`） | **毎ターン**必ず載る |
| 準レギュラー（`is_npc_pool = 1`） | **対象キャラ（`character_id`）がそのキャラのロアが採用されたターンだけ** |

ロアのスコープ判定には準レギュラーも含めるので（`scopeEntries` に
`participant_ids + npcPool` を渡す）、**参加キャラでなくても発火する**。
走査窓には「いま送ったユーザー発言」が入るため、名前を出したそのターンから載る。
ただし窓は直近 `lore_scan_window` 件（既定8＝4ターン）なので、名前が出てこなくなると落ちる。

**キーワードが名前でも、`character_id` が空なら定義は載らない。** 判定はロアの本文や
キーワードではなく `character_id` だけを見ている。ここは間違えやすい。

### 4.3 基準ステート

**すべての生成は「基準ステート」に差分を足して新しい `state_after` を作る。**
基準の決め方はモードごとに異なり、ここを誤ると時間が累積する。

| モード | 基準 |
|---|---|
| 通常送信 | 直前に保存した user メッセージの `state_after`（＝その前の値のコピー） |
| retry | 末尾 user の `state_after` |
| autoContinue | 末尾 assistant の `state_after` |
| **regenerate** | **対象の1つ前のメッセージの `state_after`。存在しなければ `chats.initial_state`** |

先頭メッセージの再生成で `chats.state` を基準にすると、再生成のたびに時間が積み上がる
（18:20 → 18:40 → 19:00）。これを避けるために `chats.initial_state` を持つ。

### 4.4 `chats.initial_state`

Chat作成時にシナリオからコピーした初期ステート。**以後変更しない。** 用途は2つ。

1. 先頭メッセージ再生成の基準
2. 全メッセージ削除時の復元先

シナリオを参照しないので、**シナリオを後から編集・削除しても既存Chatの挙動は変わらない**。

参加キャラも同じく作成時のコピーなので、進行中の会話へ足したい場合は
`PUT /chats/:id` の `participant_ids` を直す（会話の設定から加除できる）。
シナリオ側に足しても既存の会話には反映されない。

### 4.5 手動編集

ステート編集画面から時刻・場所・天候・在席者・進行フラグを直接変更できる。
**進行フラグの手動編集だけは `monotonic` と `system_only` を課さない**（詰まったときの救済手段）。

手動編集は `normalizeState` で値を入れ替えるだけで、**天候の抽選もイベント判定も走らない。**
これは意図した挙動で、「値を直す」ための経路だから。日付を進めたい場合は §4.6 を使う。

#### 時刻の入力は年月日時分で受ける

`ChatState.time` は通算分だが、**画面に生の数値を打たせない。**
ステート編集（`PUT /chats/:id/state` の `game_time`）とシナリオ編集
（`PUT /scenarios/:id` の `initial_state.game_time`）は、どちらも
`{year, month, day, hh, mm}` を受け取り、**サーバが `calendar.ts` の `toMinutes` で変換する。**
返すときも `toGameTime` でほどいて添える（シナリオは `initial_game_time`）。

- **クライアントでは換算しない。** 暦は世界ごとに違う（月数・日数・曜日名）ので、
  持たせると二重実装になる
- 派生値は**保存する形に混ぜない**。`game_time` はルートで消してから
  リポジトリへ渡す（`updateScenario` は `initial_state` を素で混ぜるため、
  残すとDBのJSONへ焼き付く）
- 5つ揃っていないときは無視して `time` の直接指定を通す（書き出し・取り込みの経路）

### 4.6 場面を進める（`POST /chats/:id/advance`）

時間を動かしたいだけで、生成はしたくない場合の経路。手動編集との違いは
**「遷移として扱うかどうか」** の一点で、こちらは生成ターンとまったく同じ関数を通る。

1. `applyDelta` — 日付が変われば天候を抽選し直す。種も生成時と同じ
   （`chatId:weather:通算日`）なので、同じ日に着けば同じ天気になる
2. `runEventPipeline` — `on_day_change` / `on_location_change` / `on_enter` /
   `chance` / `once_per_day` が生成ターンと同じに効く
3. 採用イベントの `set_vars` 適用と発火記録

LLMは呼ばない。要約・知識抽出もここでは起動しない
（LLMを呼ばない操作から呼び出しが飛ぶのは分かりにくいため。次の生成ターンで判定される）。

**場面転換マーカーのメッセージを1件挿入する。** 表示のためだけではなく、必須の理由が2つある。

1. 発火は assistant のメッセージに紐づき、次ターンの注入はそこから引く（§9.2）。
   マーカーを作らずに直前の応答へ紐づけると、その応答の発火と混ざって再注入される
2. 基準ステートは「直前メッセージの `state_after`」なので、鎖を繋いでおく必要がある

`messages.role` は CHECK で `user`/`assistant` に固定されており、SQLiteでは表を
作り直さないと変えられない。そのため種別は `messages.kind`（`normal` / `scene_break`）で持つ。
本文は `――秋・第2週の水曜日 08:00、古書店。` のような地の文で、モデルから見ても
自然な場面転換として読める。**マーカーは生成された応答ではないので再生成の対象にしない。**

複数日をまとめて進めた場合、天候の抽選も `on_day_change` の判定も**1回だけ**行われる。
これは `elapsed_minutes` に同じ値を入れた生成ターンと同じ挙動で、意図的に揃えている。

## 5. 生成フロー

実装: `server/src/routes/messages.ts`

### 5.1 応答フォーマット

モデルには話者ラベル付きプレーンテキストを書かせる。

```
アシュリー: 本を閉じて顔を上げた。「いらっしゃい」

@@@STATE
elapsed_minutes: 20
location: vein_bookstore
present_add:
present_remove:
set_var: toby_met=true
@@@END
```

- 行頭 `話者名: ` が発話の区切り。セリフは `「」`、それ以外は地の文
- 1発話 = 1吹き出し。段落で発話を分けない
- その場限りの脇役は `NPC[店主]: ` の形式。登録済み人物をこの形式で書かせない
- `*` や `_` で地の文を囲ませない

### 5.2 話者の解決順

`llm/parse.ts` の `resolveSpeaker`。**上から順に見て、最初に当たったところで決める。**

1. 参加キャラの名前・別名
2. ペルソナ名 → 代弁として扱う（§5.8 で本文を切り詰める）
3. 「ナレーター」完全一致
4. 準レギュラーの名前・別名 → **自動参加を「提案」**（勝手に参加させず確認ダイアログを出す）
5. `NPC[...]` 形式 → その場限りの脇役
6. 該当なし → 直前の発話に本文として連結

同じ順位の中で複数当たった場合は**一致した文字列が長い方**を採る（別名より本名が優先）。

**この順序が効くのは `sanitizeResponse` を通ったあとの本文だけ。**
ペルソナ名と同じラベルの行は、その手前（§5.8）で本文ごと切り落とされるため、
`resolveSpeaker` には届かない。つまり **ペルソナ名との衝突は解決順では解決しない。**

| ペルソナ名が… | 起きること |
|---|---|
| 参加キャラ名（または別名）と同じ | そのキャラの発話行以降が消える。1人しか喋っていなければ本文が空になる |
| 「ナレーター」と同じ | 地の文の行以降が消える。地の文で始まる応答は丸ごと空になる |
| 準レギュラー名と同じ | その準レギュラーの発話行以降が消える |

いずれも設定の問題なので、**生成のたびに衝突を警告として返す**（`personaCollisions`）。
切り落とした結果として本文が空になった場合は、`生成結果が空でした` だけで終わらせず
その理由を添える。原因が分からないまま「応答が途中で切れる」と悩むことになるため。

### 5.3 ストリーミング

SSE。`delta` → `done` / `error`。

**`@@@STATE` 以降は画面に流さない。** 判定のため、末尾 `@@@STATE` の文字数分は常に保留してから
送出する（フェンスの断片が一瞬見えるのを防ぐ）。

`max_tokens` は設定値 +200 で発行する。本文が上限に達してフェンスが切れるのを緩和するため。

### 5.4 同時生成の防止

チャットIDごとに `AbortController` を `inflight` Map で保持する。
二重生成は 409（「他の端末で生成中です」）。`POST /chats/:id/stop` で中断できる。

**ロックは受付直後に取り、ステート確定まで保持する。**

取得が遅いと、`inflight.has` を通ってから `inflight.set` までの間に別のリクエストが入る。
その間に user メッセージの保存とコンテキスト組み立てがあり、組み立てはモデル情報の取得で
待つことがある（`listModels` のキャッシュが冷えているとき）ので、隙間は実在する。
2本とも通ると user が二重に保存され、`AbortController` も後から `set` した方で上書きされる。

順序は「チャット存在確認 → mode の検証 → `inflight.has` → `set` → 以降すべて」。
400 / 413 / 500 のどの経路で抜けても外れるよう、`releaseLock()` は冪等にして
ハンドラ末尾の `finally` でも呼ぶ。

解放が早すぎても壊れる。LLMのストリームが終わった時点で外すと、
assistant・候補・発火履歴・`chats.state` を書き終える前に次のターンが始まり、
古い `lastMessage` を基準にしてしまう。メッセージの並び自体も
`user, user, assistant, assistant` のように崩れる。
区間は「ストリーム完了 → parse → assistant/候補の保存 → イベント判定 → `setChatState`」で、
`try/finally` で必ず解放する。`done` 以降の要約・知識抽出は区間に含めない
（数十秒かかるうえ、次のターンを止める理由がない）。

### 5.5 stop シーケンス

`["\n{ペルソナ名}:", "\nuser:"]`。先頭の改行は1文字目での誤停止対策。

### 5.6 フェンス欠落

パースできなかった場合は `elapsed_minutes: 10`・他は変更なし、で進める。

`elapsed_minutes` の値は `parseDurationMinutes`（`llm/parse.ts`）で読む。
**数字だけを拾って連結しない。** 以前は `value.replace(/[^\d-]/g, '')` だったため
「1時間30分」が130分になっていた。ゲーム内時刻はここから直接進むので、
誤読はそのまま履歴に残る。受けるのは次だけで、それ以外は既定値＋警告に落とす。

| 書き方 | 分 |
|---|---|
| `10` / `90` / `-5` | そのまま（負値は `applyDelta` が0にする） |
| `90分` / `30m` / `45 min` | 90 / 30 / 45 |
| `2時間` / `2h` | 120 |
| `1時間30分` / `1h30m` | 90 |
| `約10分ほど` など | 読めない → 10分で進めて警告 |

時刻を読む `parseHhmm` とは別物（あちらは「18:30」という時点、こちらは長さ）。

**チャットごとに連続欠落回数を数え、3回でUIに警告を出す**（メモリ上。1回でも成功すればリセット）。

原因の切り分けができるよう、抽出方式を「別コール抽出」に切り替えられる（§14）。

### 5.7 生成の中断・失敗

| 状況 | 保存 | `generation_status` |
|---|---|---|
| 正常終了 | する | `complete` |
| 途中で停止（本文が1文字以上） | **ここまでを保存する** | `stopped` |
| 停止が早く本文が空（ヘッダ受信前など） | **保存しない**（末尾がuserのまま残り retry できる） | — |
| 上流の無応答でタイムアウト | **保存しない**（同上）。理由を明示したエラーを返す | — |
| 通信・API失敗 | **保存しない**（同上） | — |

**`stopped` ではイベント判定を走らせない**（§9.2）。

**停止操作と通信の失敗を混ぜない。** `streamChat` は結果に `outcome`
（`'complete' | 'user_abort'`）を持たせ、呼び出し側はこれで分岐する。
レスポンスヘッダが返る前に `/stop` が来ると `fetch` 自体が `AbortError` を投げるので、
読み取りループだけでなく `fetch` も同じ例外処理の対象にする。
ここを外すと、利用者が自分で押した停止が「This operation was aborted」という
通信エラーとして画面に出る。`messages.ts` 側にも
「`abort.signal.aborted` なら停止として扱う」受け皿を置いて二重に守る。

#### 待ち時間の上限

**上限が無いと上流の沈黙でロックが永久に残る。** 生成ロックは `finally` で外すので、
`reader.read()` で止まったままだとそこへ到達できず、そのチャットは以後ずっと409になり、
プロセスを再起動するしか戻せない。

| 種類 | 計る区間 | 既定 | 環境変数 | `outcome` |
|---|---|---|---|---|
| 接続確立 | fetch開始 → レスポンスヘッダ受信 | 60秒 | `STREAM_CONNECT_TIMEOUT_MS` | `connect_timeout` |
| idle | 最後にデータが届いてから次が届くまで | 60秒 | `STREAM_IDLE_TIMEOUT_MS` | `idle_timeout` |

2つに分けるのは、接続確立がモデルのキュー待ちで長引くことがあり、
ストリーム開始後の沈黙とは意味が違うため。

**タイムアウトは `stopped` として握り潰さない。** 停止操作と同じ扱いにすると、
中途半端な本文が保存されるうえ原因が利用者に伝わらない。受信済みの本文は破棄し、
「何秒待って、何文字を捨てたか」を含むエラーを返して retry させる。

### 5.8 後処理の順序

```
フェンス分離 → サニタイズ → 発話パース → applyDelta
  → メッセージ／候補の保存 → イベント判定パイプライン（complete時のみ）
  → chats.state 更新 → 要約・抽出のバックグラウンド起動 → done送出
  → 要約・抽出の完了を待って notice 送出 → ストリームを閉じる
```

**フェンス分離を先にする。** `sanitizeResponse` はペルソナ名（または `user:`）の行で
そこ以降を捨てる。`@@@STATE` は本文の後ろに付くので、逆順にすると
「代弁 → フェンス」という応答でフェンスまで消え、フェンス欠落として
`fallbackDelta(10)` と `fenceMissStreak` の加算が起きる。
利用者には「モデルが `@@@STATE` を書かない」と見えるが、実際の原因は代弁である。

`sanitizeResponse` は切り詰めたかどうかを `impersonated` で返し、
呼び出し側はフェンス欠落とは別の警告として画面へ出す。

### 5.9 notice — バックグラウンド処理の結果を返す

自動要約・自動抽出は生成の後ろで走るので、成否がどこにも出ない。
**「静かに失敗した」を作らないため、結果を必ず画面へ返す。**

- `maybeSummarize` / `maybeExtract` は `{ needed, done: Promise<Notice | null> }` を返す
- `done` を送ったあと（＝画面はもう待っていない）に `done` を待ち、`notice` イベントで流してから閉じる
- `runSummarize` / `runExtract` は**例外を投げない**。バックグラウンド実行では投げても理由が誰にも届かないため、
  必ず `{ ok, message }` を返す
- 待ち時間は 60 秒で打ち切る。打ち切っても処理自体は最後まで走る（通知が出ないだけ）
- `inflight` は生成の終了時に解放済みなので、待っている間も次のターンを始められる
- ストリームを開けたまま待つので、その間に画面を閉じられ得る。
  切れたソケットへの書き込みで落とさないよう `send` で防ぐ

要約が空応答を返した場合は「変更なし」ではなく**失敗**として扱う。
黙って流すと、あらすじが更新されないまま毎ターン再挑戦することになる（§10.2 と同じ方針）。

### 5.10 履歴の読み込み（ページング）

`GET /chats/:id` は**末尾40件だけ**返す。全件返すと、画像付きの長い会話を開いたときに
読み込みが一気に嵩む。応答に `total` と `hasMore` を添え、画面は「さかのぼる（残りn件）」を出す。

- それより前は `GET /chats/:id/messages?before_seq=S&limit=N`（昇順で返す）
- `limit` は1〜200に丸める。0や負の値で全件・空にならないようにする
- **スナップショットのメタは全件同梱する。** 1件数百バイトで、遡ったときにそのまま使える。
  画像の実体は読まないので重くならない
- 画面側の注意が2つある。**末尾へ寄せる副作用の依存は「末尾のID」**にすること
  （件数にすると、古い分を足しただけで一番下へ飛ぶ）。
  もう1つは**足した直後にスクロール位置を戻す**こと。`useLayoutEffect` で
  「増えた高さ」を `scrollTop` に足す（`requestAnimationFrame` ではReactの反映前に
  走ることがあり、位置がずれる）
- 再生成・分岐・編集・削除のあとの再読み込みは末尾40件に戻る（単純さを取る）

## 6. プロンプト組み立て

実装: `server/src/llm/prompt.ts`

### 6.1 メッセージ構成

```
[system]  ← 下表の順に連結した1本
[user/assistant] × 履歴窓
[system]  ← 現在の状況ブロック（末尾system）
```

**状況ブロックを末尾に置く。** 後ろほど強く参照されるため、直近の事実をここに集約する。

履歴窓は**あらすじの境界（`up_to_seq`）より後**から最大 `history_window` 件を取る。
要約済みの範囲は生では送らず、あらすじが肩代わりする。

### 6.2 system の順序

| # | ブロック | 削減対象 |
|---|---|---|
| 1 | 応答フォーマット指示 | — |
| 2 | 進行フラグの更新指示（有効かつ書き込み可能なキーがあるときのみ） | — |
| 3 | 設定情報の扱い | — |
| 4 | アプリ共通のシステムプロンプト | — |
| 5 | 世界のシステムプロンプト | — |
| 6 | シナリオ設定 → 参加キャラ定義 | — |
| 7 | 準レギュラーの定義（**関連ロアが発火したときだけ**） | — |
| 8 | ナレーター指示 → ペルソナ定義 | — |
| 9 | メモリー | ⑤ |
| 10 | あらすじ | — |
| 11 | 関連する世界観情報（ロア） | ③④ |

### 6.3 末尾systemのブロック順序

**この順序は固定とする。**

```
# 現在の状況        ← 事実
# 進行状況          ← 物語の段階（§8）
# 発生中の出来事    ← 今起きていること（§9、inject_mode = fact）
# 今回の演出指示    ← どう書くか（§9、inject_mode = instruction）
```

事実を読ませてから「どう出すか」の指示を当てる。逆順にすると指示が事実に埋もれる。

### 6.4 「現在の状況」の中身

```
# 現在の状況
3年8月10日（秋・第2週の火曜日） 18:30 ／ 場所:ヴェイン古書店 ／ 天候:霧
日没後（日の出 08:10 ／ 日没 16:20）。
〈無銘〉は営業中。〈マルロウ〉は閉店済み。
終電まであと40分。
その場にいる人物:アシュリー
場所ID: vein_bookstore=ヴェイン古書店, ...
人物ID: 01xxx=アシュリー, ...
日付が変わり、天候は霧になった。
```

- 屋内にいるときは天候行を出さない
- 営業状況は**現在地と同じエリア**の店のみ。`location_note` 使用中は出さない
- 終電行は通知窓（既定60分前）の中だけ
- 最終行は日付が変わったターンのみ

**年月日を渡す。** あらすじは `[3年8月10日(火)]`、メモリーは `(3年8月7日(土) / 3日前)`（§10.2）の形で
日付入りの情報を渡しているのに、現在日付が無いと突き合わせられない。
「モデルに時刻を書かせない」規則（§5.1）は本文の書き方の話であり、参照点として
渡すこととは衝突しない。週・曜日も感覚として有用なので併記する。

**日の出・日没は時刻も添える。** 状態（日の出前 / 日中 / 日没後）だけだと
「あと何時間明るいか」が書けない。

場面転換マーカー（§4.6）は表示にも使うので、そちらは `formatGameTime`
（`秋・第2週の水曜日 08:00`）のまま。日時の表記関数は用途ごとに分ける。

### 6.5 予算

```
入力予算 = モデルのコンテキスト長 − (max_tokens + 200) − context_safety_tokens
```

日本語は保守的に `文字数 × 1.1` トークンで見積もる。超過時の削減順は固定。

```
① 履歴の古い方（最低2件は残す）
② キーワード発火のロア（priority 昇順）
③ 場所・季節タグのロア（priority 昇順）
④ メモリー（ピン留め以外を、古い順に1件ずつ）
```

`always` のロアと**ピン留めのメモリー**は削減対象にしない
（文字数には数えるが、落とさない）。必須項目だけで超過したら **413** を返す
（黙って切り詰めない）。

**メモリーは1件ずつ落とす。** キャラ単位のブロックごと落とすと、1件超えただけで
その人物の記憶が全部消える。落とす順は `created_at` 昇順（古い順）で、
ピン留めは候補に入れない。

**ロアだけは二段構え。** `lore_budget_chars`（既定12,000文字）で発火時に採用を絞ってから、
この全体予算にも乗る。メモリーに専用予算は無い。

## 7. ロアブック

### 7.1 スコープ

以下を**すべて**満たすエントリだけが判定対象。

`lore_recursion`（1〜4）。発火したエントリの本文を走査対象に足して、もう一巡する。

## 8. 進行フラグ

実装: `server/src/domain/vars.ts`

### 8.1 目的

「事件がどこまで進んだか」「もう会ったか」といった**物語の状態**を、時刻や場所と同じく
アプリが持つ。モデルの記憶や、あらすじの文面に頼らない。

### 8.2 スキーマ

`worlds.vars_schema` にキーを定義する。**ここに無いキーは誰も書き込めない**
（誤字による野良キーの増殖を防ぐ）。

```ts
{
  key: string;              // 英字始まりの識別子
  type: 'number' | 'boolean' | 'string';   // string は32文字まで
  role?: 'flag' | 'phase';
  default?: VarValue;
  label?: string;
  min?: number; max?: number;              // 範囲外は丸める
  monotonic?: boolean;                     // true なら後退する更新を棄却
  update_mode?: 'system_and_llm' | 'system_only';
  phases?: { value, name, public_state?, private_note? }[];
}
```

上限は 64件（`MAX_VARS`）。

### 8.3 更新経路と権限

| 経路 | `system_only` | 範囲外 | `monotonic` |
|---|---|---|---|
| モデル（`set_var:`） | **破棄**して警告 | 丸める | 棄却 |
| イベント（`set_vars`） | 更新できる | 丸める | 棄却 |
| 手動編集 | 更新できる | 丸める | **通す**（救済手段） |

### 8.4 `public_state` と `private_note`

`phases` の `public_state` は「進行状況」ブロックに載る。
**`private_note` はプロンプトへ一切載せない。** 作者が構成を見失わないためのメモ欄であり、
`buildVarsBlock` は `public_state` のみを読む。この不変条件はテストで固定している。

### 8.5 初期化

Chat作成時に `vars_schema` の `default` で `state.vars` を埋め、
シナリオの `initial_state.vars` で上書きする。

### 8.6 無効時の挙動

`vars_enabled` が偽のとき、進行フラグは**存在しないものとして扱う**。

- 「進行状況」ブロックを出さない
- `set_var` の指示文を出さない
- モデルの `set_var` を適用せず警告のみ残す（**既存の値は保持する**）
- 条件式の `var` 述語は常に偽

## 9. 条件付きイベント

実装: `server/src/domain/events.ts`

### 9.1 判定パイプライン

上から順に評価し、1つでも落ちたら見送る。

| # | 段階 | 内容 |
|---|---|---|
| 1 | 有効 | `enabled = 1` かつ `events_enabled` が真 |
| 2 | `when` | 条件式（§9.3） |
| 3 | `check` | `every_turn` / `on_enter` / `on_day_change` / `on_location_change` |
| 4 | `trigger` | 同じスコープで発火済みでないか（§9.4） |
| 5 | `chance` | シード固定の抽選（§9.5） |
| 6 | 上限 | `priority` 降順・`id` 昇順で `event_max_per_turn` 件。**`instruction` は常に1件まで** |

各イベントがどの段階で落ちたかは `POST /worlds/:id/events/evaluate` が返す
（`adopted` / `condition` / `check` / `trigger` / `chance` / `capped`）。

### 9.2 実行タイミング ★v1.4からの変更

**判定は assistant の生成が完了し `state_after` が確定した直後にのみ走り、
注入は次のターンのプロンプトに載る。**

v1.4 では「生成前に基準ステートで判定し、そのターンに注入」していた。
これだと「カフェに着いた」応答が返る前に「店内は混んでいる」が注入され、
まだ起きていない事象を前提に書かせてしまう。

- 途中で停止した生成（`stopped`）では判定しない。次のターンで改めて判定する
- `set_vars` の適用と発火記録は**1トランザクション**で行う。書き戻した `state_after` は
  メッセージ本体と表示中の候補の両方に反映する
- 「場面を進める」（§4.6）でも同じパイプラインが走り、発火はマーカーに紐づく

**注入の窓は「発火した次の1ターン」だけ。** 注入は `firesAtMessage(直近のassistant)` で引くので、
次のターンで新しい assistant が生まれた時点で前回分は落ちる。持続させたい効果は
`trigger: repeat` + `check: every_turn`、または進行フラグを立てて
それを条件にする2段構えで表現する（§8）。

**注入元は「履歴の末尾」ではなく「直近の assistant」。**
送信時はユーザー発言を先に保存してからプロンプトを組み立てるため、末尾を見ると常に
`user` を指してしまい、発火は assistant にしか紐づかないので何も注入されない。
プロンプトプレビューはユーザー発言を挟まずに組み立てるので末尾が assistant になり、
**プレビューでは見えるのに実際の生成には効かない**という形で表面化する。
回帰テストはプレビューではなく、モックが受け取った実際のプロンプトを見ること。

### 9.3 条件式

オブジェクトの複数キーは AND、配列で与えた値は OR。`all` / `any` / `not` で入れ子にできる。

| 述語 | 例 |
|---|---|
| `season` / `month` / `week` / `weekday` | `{ "month": [9, 10] }` |
| `time_after` / `time_before` | `{ "time_after": "17:00" }` |
| `location` / `location_area` | `{ "location_area": ["harbor"] }` |
| `weather` | `{ "weather": ["雨", "雪"] }` |
| `present_has` / `present_lacks` | `{ "present_lacks": "toby" }` |
| `var` + `eq`/`ne`/`in`/`gt`/`gte`/`lt`/`lte` | `{ "var": "case_phase", "gte": 2 }` |

**`location_note` 使用中は場所系の述語を常に偽とする**（エリアを導出できないため）。
`vars_enabled` が偽のとき `var` 述語は常に偽。

#### 保存時の検証（`validateCondition`）

述語は「該当しなければ次を見る」構造なので、**知らないキーは最後まで落ちずに真になる。**
`{ "seazon": "秋" }` のような誤字が「発火しない」ではなく「常に発火する」へ振れてしまうため、
評価器と述語一覧を共有するバリデータを同じファイルに置き、保存時に弾く。

| 内容 | 扱い |
|---|---|
| 知らないキー | 400。`when.all[1].seazon` のようにパス付きで返す |
| `var` の無い比較子（`{ "eq": 1 }`） | 400 |
| 比較子を2つ以上（`{ "var": "x", "gte": 1, "lte": 3 }`） | 400 |
| 読めない `time_after` / `time_before` | 400 |
| 実在しない場所ID・エリアID・`vars_schema` に無いキー | 400 |
| 値の型違い（`month` に文字列など） | 400 |
| `time_after` > `time_before`（日跨ぎ） | 保存する。`warnings` で返して画面に出す |

**取り込み（復元）は検証しない。** 1件の誤字で世界全体の復元を止めないため。
そこから入ったものと、検証を入れる前に保存されたものは
**評価時に「満たさない」へ倒す**（`time_after` の読めない表記と同じ扱い）。

### 9.4 トリガーとスコープ

| `trigger` | `scopeKey` |
|---|---|
| `once` | `'once'` |
| `once_per_day` | 通算日 |
| `once_per_visit` | 訪問ID（`location_note` 使用中は特定できず見送り） |
| `once_per_phase` | `{trigger_var}:{現在値}` |
| `once_per_year` | 通算年 |
| `cooldown` | スコープなし。前回発火から `cooldown_days` 経過で再発火 |
| `repeat` | スコープなし。履歴を見ない |

発火履歴は**チャット単位**。別のチャットでは改めて発火する。

### 9.5 抽選のシード

```
seed = `${chatId}:${eventId}:${drawKey}`
drawKey = scopeKey ?? (check === 'on_day_change' ? 通算日 : 基準メッセージID)
```

**スコープを持つ trigger では `drawKey` を `scopeKey` で「置き換える」（連結しない）。**
連結すると、再生成のたびに基準メッセージIDが変わり抽選をやり直せてしまう。

天候も同じ考え方で `${chatId}:weather:${weatherDayOf(...)}` をシードにする。
**再生成しても同じ日なら同じ天気になる。**
種の境界は判定と同じ `weatherDayOf` を通すこと（§12.3）。

### 9.6 履歴の整合

| 操作 | 発火履歴 |
|---|---|
| 再生成 | **対象メッセージの履歴を削除してから再判定**（作り直した候補で改めて判定する） |
| 分岐（fork） | 分岐点までの履歴を引き継ぐ（分岐先で二重に起きない） |
| メッセージ削除 | そのメッセージ以降（`seq` 基準）の履歴を削除 |
| 手動取り消し | ステート編集画面から1件ずつ削除できる |

### 9.7 フェーズ遷移の欠落チェック

`GET /worlds/:id/events/phase-check` が、**どのイベントの `set_vars` からも到達できないフェーズ**を返す。
「フェーズ3を作ったのに3にするイベントが無い」という作り忘れを見つけるためのもの。

## 10. 要約とメモリー

### 10.1 要約 — `server/src/domain/summary.ts`

未要約メッセージが `summary_interval` 件たまったら、バックグラウンドで実行する。

```
retain = min(24, max(2, floor(interval / 2)))   ← 直近この件数は要約せず生で残す
retain = min(retain, n - 2)                     ← 1回で最低2件は前へ進める
対象 = 未要約の先頭から (n - retain) 件
発火間隔 = interval - retain ≒ interval / 2 メッセージ
```

**`retain` は `summary_interval` に比例させること。** 以前は interval と無関係に24件で
頭打ちにしていたため、interval が小さいと retain が interval をほぼ食い尽くし、
1回で2件しか進まず、次のターンで即座に閾値へ戻って**毎ターン要約**になっていた。

| interval | 旧: 発火間隔 | 新: 発火間隔 |
|---|---|---|
| 16 | **毎ターン** | 4ターン |
| 24 | **毎ターン** | 6ターン |
| 32 | 4ターン | 8ターン |

設定画面には実際の発火間隔（`summarizeEveryMessages`）を出す。
2つのつまみが噛み合っているかは、値を見ないと分からないため。

**前回のあらすじと今回の対象範囲を統合して1本に書き直させる。**
前回分を捨てて新規分だけ要約する実装を禁止する（古い出来事が消えるため）。

境界は `summaries.up_to_seq` に記録する。

#### プロンプトは骨組みと方針に分ける

要約プロンプトは2層で組む。**利用者が編集できるのは方針だけ**とする。

| 層 | 内容 | 編集 |
|---|---|---|
| **骨組み**（`buildRules`） | 統合の指示／前回分を落とさない／人物設定を書かない／日付の形式／文字数／本文のみ出力 | 不可 |
| **方針**（`settings.summary_policy`） | 何を残すか・何を落とすか・文体・構造 | 可 |

骨組みを編集可能にしない理由は、そこにアプリの構造上の制約が入っているため。
統合の指示を落とせば古い出来事が消え、人物設定の除外を落とせばロアブックと
二重管理になってコンテキストを食う。**どちらも黙って起きる。**

#### 「何を落とすか」を必ず書く

以前の骨組みには「**古い出来事も消さずに残し、N文字程度に圧縮する**」とあった。
これは「何も捨てるな、でも短くしろ」であり、モデルにできるのは文を詰めることだけになる。
結果は接続詞で繋いだ列挙（＝冗漫なあらすじ）で、**長さは守られるのに読めない**。

既定の方針（`DEFAULT_SUMMARY_POLICY`）は「何を残すか」と対で
**「何を落とすか」**（雑談・日常動作・転機でない感情描写）を持つ。

#### 前回分と今回分で扱いを変える

- **前回までのあらすじ** — 既に選別済み。言い回しは縮めてよいが項目は落とさない
- **今回の会話** — 生の記録。方針に従って取捨選択する

この区別が無いと、「落とす」指示が過去のあらすじにも効いて古い出来事が消える。

`settings.summary_policy` が空文字のときは既定へ戻す（骨組みだけになるのを防ぐ）。

### 10.2 メモリー — `server/src/domain/memory.ts`

キャラごとの長期記憶。会話をまたいで保持する。

| 項目 | 意味 |
|---|---|
| `subject` 空 | 常時注入 |
| `subject` あり | その人物が**在席中**、または**関連ロアが発火**したときだけ注入 |
| `pinned` | 予算削減の対象から外す |
| `source` | `manual` / `auto`（自動抽出） |
| `game_time` | その出来事のゲーム内時刻（通算分）。`NULL` は日付不明 |
| `enabled` | `0` で注入しない。記録としては残す（§10.2「消さずに黙らせる」） |

抽出済み境界は `chats.extracted_up_to_seq`。

#### 注入のオンオフ（`enabled`）

「もう出てこなくていいが、あった事実は残したい」ためのもの。ロアブックの `enabled` と同じ考え方で、
**削除の代わりに黙らせる**。既定は 1 で、既存データもすべて 1（挙動は変わらない）。

`enabled = 0` は `assembleContext` の注入対象から外れるだけで、一覧・書き出しには残る。

**重複除けには `enabled = 0` のものも渡す。** OFF は「もう出さなくていい」という意思表示なので、
既存の記憶から外すと自動抽出が同じ内容を拾い直し、何度でも復活してしまう。

#### ゲーム内日付（`game_time`）

`created_at` は実時間なので、モデルには「いつの話か」が伝わらない。
自動抽出では**根拠になった発話の `state_after.time`** を入れ、
プロンプトへは `- (3年8月7日(土) / 3日前) …` の形で注入する。

**どの発話が根拠かはモデルに答えさせる。** 抽出は範囲（既定32件）をまとめて1回なので、
そのままでは分からない。会話を `[1] …` と番号付きで渡し、出力へ `at`（発言番号）を足させる。
`at` が無い・数値でない・範囲外なら**範囲末尾へ落とす**（番号を返さないモデルでも、
番号を振る前と同じ結果になるだけで劣化しない）。番号付きで渡す副作用として
`content` に `[3] ` を混ぜてくるモデルがあるので、プロンプトで禁じたうえで先頭の
`[数字]` は落とす。

範囲が日をまたぐと——特に「場面を進める」で数日飛ばしたとき——末尾に寄せる作りでは
数日前の出来事まで今日の日付になっていた。

**絶対日付は常に出す。** あらすじの `[3年8月10日(火)]` や「現在の状況」の日付と
突き合わせられるようにするため。相対表記はそこへ添える形で、意味が通るときだけ付ける。

メモリーはチャットではなく**キャラクターに紐づく**ため、同じ世界の別チャットが
別の日付にいると差が負になったり極端に開いたりする。そこで**絶対値で保存し**、
相対表記は次のように切り替える。

| 現在との差 | 表記 |
| --- | --- |
| 0日 | `3年8月10日(火) / 今日` |
| 1日 | `3年8月9日(月) / 昨日` |
| 2日〜1年 | `3年8月7日(土) / 3日前` |
| 1年より前 | `1年1月1日(日)`（絶対日付のみ） |
| 未来（記憶の方が先） | `3年8月20日(金) / まだ起きていない出来事` |

未来側を明示するのは、絶対日付だけだと「ずっと昔の記憶」と見分けが付かないため。
一覧APIは「いまが何日か」を持たないので常に絶対日付のラベルだけを返す。

既存行と手動追加は `NULL` のまま。**実時間からゲーム内時刻は逆算できず、
推測で埋めると嘘の日付が入る。** 日付が無いものは日付を付けずに注入する。

**あとから手で設定できる。** メモリー編集画面で年月日を入れる。
通算分 ↔ 年月日の変換は暦に依存するので、APIは `game_time_parts`（年月日）で受けて
サーバ側で `toMinutes` に通す（§4.12: 時刻演算は `calendar.ts` に一本化）。
記憶に使うのは日付だけなので時刻は 0:00 に寄せる。

- `game_time_parts` を送らなければ現状維持（本文だけ直しても日付は消えない）
- `game_time_parts: null` で日付なしに戻す
- 一覧APIは編集欄の初期値用に `game_time_parts` も返す

#### 過剰抽出を防ぐ3点

自動抽出は放っておくと些細な動作・一時的な感情・雑談まで拾う。原因は
「件数の枠を与えること」と「狭い範囲から絞り出させること」の2つで、次で抑える。

1. **実行中ガード。** 要約・抽出とも、同じチャットで走っている間は再入しない。
   要約はLLM呼び出しで数秒〜十数秒かかり、その間は未要約件数が減らないため、
   ガードが無いと**毎ターン起動する**（さらに要約が失敗し続けると永久に毎ターンになる）
2. **最小範囲（`MIN_EXTRACT_MESSAGES = 8`）。** 新規メッセージがこれ未満なら抽出しない。
   1〜2件から抽出させると、モデルは些細なものを拾うしかなくなる
3. **プロンプトに件数の上限値を書かない。** 「最大N件」は上限ではなく**目標**として働く。
   代わりに「該当なしが通常」「件数を埋めるための抽出を禁止」と明示する。
   実装側の上限（5件）は超過分を黙って切り捨てるだけで、モデルには伝えない

#### 保存の条件（すべて満たすものだけ）

1. 数シーン後にも有効である
2. 将来の会話・判断・行動へ影響する
3. 忘れると明確な矛盾または不自然さが生じる
4. 単なる動作、一時的な感情、その場限りの雑談ではない
5. 既存の記憶と重複しない

③が最も効く。他が「重要か」という主観なのに対し、③だけは反証可能なため。

#### `subject` は必ず実在のIDにする

`subject` は「その人物が在席中のときだけ注入する」判定に使う。**未知の文字列が入ると
どの条件にも一致せず、保存されているのに永久に注入されない。** そのため
プロンプトに `ID = 名前` の一覧を渡し、保存時にも既知のIDか検証して、
解決できなければ空文字（＝常時注入）へ落とし、その旨を通知する。

#### 出力の上限は本文と別枠（`utility_max_tokens`）

要約・抽出の `max_tokens` は **`settings.max_tokens`（本文の生成用）とは別**。
以前は 2048 の直書きで、上限に当たっても案内が「設定の『最大トークン』を見直せ」だったため、
**本文側を上げても直らない**（そして何を上げればいいか分からない）状態だった。

- 抽出: `max(256, utility_max_tokens)`
- 要約: `max(utility_max_tokens, summary_max_chars × 2)` — あらすじの必要量が上回ればそちらを採る
- 失敗の文言には**実際に使った値**を入れる（`要約・抽出の最大トークン 8192`）

既定を 8192 と大きめに置いたのは、**推論（thinking）を行うモデルでは考えている分も
出力トークンから引かれる**ため。2048 では本文を書き始める前に打ち切られることがある。

#### 応答が読めないときは「該当なし」にしない

抽出は失敗しうる。**失敗と「保存に値するものが無かった」を混同してはならない。**

- `complete()` は `finish_reason` と `refusal` も返す。本文が空でも理由を説明できるようにする
- JSONモードで空を返すモデルがあるため、空応答なら**素のプロンプトで1度だけ試し直す**
  （拒否・長さ超過は再試行しても同じなので、そのまま理由にする）
- コードフェンスや前置きを付けるモデルがあるため、`{` 〜 `}` を切り出してから `JSON.parse` する
- 失敗の理由（空応答／長さ超過／拒否／解析不能）は `notes` に入れて画面へ出す

**失敗したら `extracted_up_to_seq` を進めない。** 進めるとその範囲は二度と抽出されず、
モデルの設定を直しても取り返せない。ただし毎ターン叩き直さないよう、
失敗後は未抽出がさらに1間隔ぶん貯まるまで自動実行を見送る。

#### 抽出の契機

`auto_extract` は **`auto_summarize` とは独立**に判定する
（自動要約を切っても自動抽出は動く）。間隔は `summary_interval` を共用する。

`POST /chats/:id/extract-preview` は**保存せずに候補と理由だけ**返す。
抽出条件を調整するための確認用で、最小範囲の判定も無視する。

見た候補をそのまま保存するのが `POST /chats/:id/extract/commit`。
**`/extract` を呼び直さない**のは、抽出のコールをもう一度払ううえ、モデルの出力は
毎回同じとは限らず「見たものと保存されるものが違う」ことになるため。
自動抽出が失敗し続けたとき（クレジット切れなど）の立て直しにも使う。

中身はクライアント由来なので、サーバで引き直す:

- `character_id` は**そのチャットの参加キャラ**に限る。外れたものは保存せず件数を返す
- `subject` は既知の人物IDでなければ空文字（＝常時注入）へ落とす
- `game_time` は申告させない。受け取るのは根拠の発話の **`at_seq`（メッセージの seq）** だけで、
  `現在の境界 < at_seq <= toSeq` を確かめたうえで**DBから時刻を引き直す**。
  欠落・範囲外なら `toSeq` のメッセージの `state_after.time` へ落とす
- `toSeq` は現在の境界より後、かつ実在する seq であること

保存したら**抽出済み境界を進める**（進めないと自動抽出が同じ範囲を拾って重複する）。
失敗後のバックオフもここで解除する。

## 11. 候補・再生成・分岐

### 11.1 候補（variant）

再生成すると同じメッセージに候補が増える。**初回生成でも必ず index 0 の候補を作る**
（後から再生成したときに元の応答が失われないようにするため）。

`messages` 側の `content` / `utterances` / `state_after` は**表示中の候補のコピー**。
候補を切り替えると、この3つと `active_variant` を差し替える。

`UNIQUE(message_id, "index")` をDBで保証する。

### 11.2 過去メッセージの扱い

**過去メッセージの候補めくりは行わない。** 途中の候補を切り替えると、それ以降の
`state_after` がすべて不整合になるため。過去の分岐点で別の候補を選ぶ操作は
**fork に一本化する**。

### 11.3 fork

```
POST /chats/:id/fork { message_id, variant_index? }
```

- 分岐点までのメッセージと候補をすべて新チャットへコピーする（`seq` は1から振り直す）
- `variant_index` を指定した場合、分岐点のメッセージだけその候補の内容で確定する
- **元チャットは一切書き換えない**
- 新チャットの現在ステートは、選んだ候補の `state_after` と一致する
- `initial_state` は元チャットのものを引き継ぐ
- 発火履歴も分岐点までコピーする

### 11.4 削除

メッセージを削除すると、`chats.state` をその1つ前の `state_after` に戻す。
**全件削除した場合は `chats.initial_state` に戻す**（シナリオを参照しない）。
`seq` 以降の発火履歴も消す。

## 12. 暦・天候・営業時間

実装: `server/src/domain/calendar.ts`

### 12.1 既定の暦と、季節の自由度

**1ヶ月28日・1年12ヶ月（＝336日）。** 週が常に第1〜第4週に収まるので、
「9月の最終週」のような指定が安定する。

```
季節: 春[3,4] 夏[5,6] 秋[7,8,9] 冬[10,11,12,1,2]
```

日の出・日没は月ごとの表を持ち、**書いていない月は前後の月から補間**する。

#### 季節名は自由

`seasons` は `Record<季節名, 月番号[]>` で、**春夏秋冬は既定値にすぎない。**
`seasonOfMonth` はこのマップを引くだけなので、名前も数も長さも世界ごとに決められる。

```json
{ "乾季": [1,2,3,4,5,6], "雨季": [7,8,9,10,11,12] }
```

1か月だけの季節（`{"台風期":[9]}`）も作れる。季節名は天候の抽選（`weather_table` のキー）、
状況ブロック、スナップショットのプロンプト、イベント条件 `season`、
ロアの季節トリガーへそのまま流れる。**ロアの季節チップは暦から作る**
（画面側に固定リストを置かない）。

#### 書き間違いは警告で返す（`validateCalendar`）

自由なぶん、月の割り当てと天候表の対応がずれても動いてしまう。
`domain/events.ts` の `validateCondition` と同じで、**保存は止めず**に指摘だけ返す。

| 検査 | 何が起きるか |
|---|---|
| どの季節にも属さない月 | `season` が空になり、日付表示が欠ける・天候が引けない |
| `1..months_per_year` の外の月番号 | その指定が永久に効かない |
| 同じ月が複数の季節に入っている | 先に書いた季節が勝つ（`seasonOfMonth` は先勝ち） |
| 季節に対応する天候表が無い | 天候が引けない（晴に固定される） |
| どの季節にも対応しない天候表のキー | 書いたのに一生使われない |
| 重みの合計が0の天候表 | 常に晴になる |

- `PUT /worlds/:id/calendar` は `{ calendar, warnings }` を返す。
  **`warnings` は保存しない**（`upsertCalendar` は浅いマージなので、
  送り返されたものをそのまま入れるとDBへ焼き付く。§4.5 の `game_time` と同じ罠）
- `GET /worlds/:id/calendar/warnings` で**開いた直後**にも出す。
  `GET /worlds/:id/calendar` の形は変えない（シナリオ編集など他の利用者がいる）

#### 天候が引けないときに、別の季節の表へ落とさない

`drawWeather` は以前、表が無いと**先頭の表**を使っていた。
「雨季」の表を書き忘れると乾季の分布で引かれ、しかも誰も気づけない。
いまは晴に固定し、`applyDelta` が `hasWeatherTable` を見て警告を積む
（生成の `warnings` → トーストという既存の経路に乗せる）。

### 12.2 内部表現

暦元期（1年1月1日 00:00）からの**通算分（整数）**のみ。
年月日時分への変換は `toGameTime` / `toMinutes` に限る。

### 12.3 天候

**1日1回だけ**、季節ごとの重み表から抽選する。
ターンごとに引くと晴れと雨が数ターンで往復してしまうため。

**切り替わりは日付の変わり目ではなく `weather_rollover_min`（既定 240 = 朝4時）。**
0:00 を境にすると、深夜に会話している最中に日付が変わった瞬間だけ天気が変わる。
RPでは日をまたぐ時間帯の会話が珍しくないので、天候だけ朝へずらす。
`0` にすると 0:00 起点（日付の変わり目と同じ）に戻せる。

```ts
weatherDayOf(cfg, time) = Math.floor((time - weather_rollover_min) / 1440)
```

- **`dayChanged` は 0:00 起点のまま。** 状況ブロックの最終行と `on_day_change` が使う。
  日付と天候は別の境界を持つ
- **`Math.floor` であること。** 起点より前（1日目の 0:00〜3:59）は商が負になるので、
  `Math.trunc` や `| 0` だと 0 に丸まって初日の4時に引き直されない
- **判定と抽選の種の両方が `weatherDayOf` を通ること。** 片方だけずらすと
  「同じ日なら同じ天気」（§20-8）が崩れる

| 時刻 | `weatherDay` | 抽選 |
|---|---|---|
| 1年1月1日 00:00 | −1 | — |
| 〃 03:59 | −1 | — |
| 〃 04:00 | 0 | 引き直す |
| 翌 03:59 | 0 | — |
| 翌 04:00 | 1 | 引き直す |

複数日をまとめて進めた場合も抽選は1回だけ（§8.3）。
抽選はシード固定（§9.5）。屋内にいるときは状況ブロックに天候行を出さない。

### 12.4 エリア

`worlds.areas` は `[{ id, name }]` の配列。**新しい世界には8件入る**
（`hilltop` / `center` / `backstreet` / `harbor` / `outskirts` / `market` / `residential` / `underground`）。

- **`name`（表示名）と並び順はいつでも変えられる**
- **`id` は作成後に変更できない。** `locations.area` とイベント条件の `location_area` から
  参照されており、後者は入れ子JSONの中にあるため、リネームを許すと条件が黙って発火しなくなる
- 場所に使われているエリアは削除できない
- 変更は `PUT /worlds/:id/areas` 専用ルートのみ。汎用の `PUT /worlds/:id` からは変えられない
  （参照チェックを迂回させないため）

### 12.5 時刻表記のパース

`parseHhmm`（`shared/types.ts`）に一本化する。**半角コロンだけを受け付けてはならない。**
日本語キーボードの既定は全角「：」なので、入力が黙って無効化され、
「保存したのに時刻が消える」「イベントが常時発火する」という形で表面化する。

受け付ける表記: `09:00` / `9:00` / `09：00` / `０９：００` / `900` / `9` / `9時` / `18時30分`

- 時は24を超えてよい（閉店 `26:00` = 翌2時）。分は0〜59
- 解釈できないときは `null` を返し、**呼び出し側が「無効」として扱う**
- **イベント条件の `time_after` / `time_before` は、解釈できないとき条件を偽にする。**
  0分に丸めると常時真になり、全時間帯で発火してしまう（誤りが広がる方向へ倒れる）
- 入力欄は制御コンポーネントにし、解釈結果（「9:00 として保存します」）をその場に出す。
  非制御 + `onBlur` にすると、blur が起きないまま保存された場合に入力が反映されない

### 12.6 営業時間と終電

- 現在地と**同じエリア**の、開店・閉店が両方設定された場所の営業状況を出す
- `close_min` は 24 を超えて書ける（`26:00` = 翌2時）
- 終電行は `last_train_min` の `last_train_notice_min` 分前から出す。
  `last_train_enabled = 0` で行ごと出さない（鉄道が無い世界観向け）。
  `last_train_label`（既定「終電」）を「最終バス」「最終転移」などに変えられる
- **暦は列ではなくJSON1本（`calendars.config`）** なので、キーを増やしてもマイグレーションは不要。
  読み出し時に `normalizeCalendar` が既定値で補う


**終端イベントが来ないまま閉じることがある**（回線断・プロキシ）。クライアントは
`done` / `error` を受け取ったかを覚えておき、ストリーム終了時にどちらも来ていなければ
自分で `onError` を呼ぶ。これが無いと、待っている側のPromiseが解決されず
生成中の表示のまま固まる。末尾の区切り（空行）が来ないまま閉じる場合もあるので、
残ったバッファも最後に1度読む。

## 16. 認証とセキュリティ

実装: `server/src/routes/auth.ts`

- **APIキーはサーバだけが持つ。** ブラウザには一切渡さない
- `APP_PASSWORD` 未設定時は認証が素通り（開発用）。**ただし公開構成では起動を拒否する（§16.2）**
- セッションはメモリ上のMap（TTL 30日）。プロセス再起動で失効する
- パスワード比較はHMACダイジェスト同士の `timingSafeEqual`（長さを揃えるため）
- 認証Cookie: `httpOnly` / `sameSite: lax` / `secure`（`COOKIE_SECURE`、未設定なら `APP_URL` が https のとき）
- リバースプロキシ配下では `TRUST_PROXY` を設定する（`req.ip` と `req.protocol` が正しくなる）
- **ログイン失敗のレート制限**: 同一IPで15分に5回失敗すると15分ロック（429）

### 16.1 到達範囲を絞る（`BIND`）

既定では全インターフェースで待ち受ける。`BIND=127.0.0.1` を設定するとループバックだけになり、
`tailscale serve` のようなフロントを経由しないと到達できなくなる。

- Tailscale等でVPN内だけに公開する場合はこれを使う。手順は README を参照
- **将来 identity ヘッダ（`Tailscale-User-Login` 等）で認証する場合、ループバック固定は必須。**
  全インターフェースで待ち受けたままヘッダを信用すると、誰でも偽装して素通りできる
- 存在しないアドレスを指定した場合は、原因を示して終了する（黙って全公開に落ちない）
- `BIND` を絞っても `APP_PASSWORD` は残す（多層防御）

### 16.2 危ない構成では起動しない

**外部から届く状態で `APP_PASSWORD` を設定していない構成は、待ち受ける前に終了する。**

警告ログだけでは、設定ミスに気づくのが「誰かに使われたあと」になる。
漏れるのは会話だけでなく OpenRouter の利用権（＝請求）でもあるので、既定を安全側に倒す。

**判定は「全インターフェースか」ではなく「到達範囲が絞れているか」で行う**（`server/src/bind.ts`）。
`BIND=203.0.113.10`（VPSの公開IP）は `0.0.0.0` ではないが誰からでも届く。
前者で判定すると、この構成がパスワード無しのまま素通りしてしまう。

絞れているとみなすのは次だけ。

| 範囲 | |
|---|---|
| `127.0.0.0/8` / `::1` / `localhost` | ループバック |
| `100.64.0.0/10` | Tailscale の CGNAT 帯。tailnet 内からしか届かない |

LANのアドレス（`192.168.x.x` など）は含めない。同じLANの他の機器から届くうえ、
「家のLANだから安全」は運用者の判断であって既定にはできない。
解釈できない文字列（ホスト名など）も安全側に倒して「絞れていない」とする。

止まらない構成は3つで、起動時のメッセージにそのまま出す。

| | |
|---|---|
| `APP_PASSWORD=<パスワード>` | パスワードで保護する |
| `BIND=127.0.0.1` など | 到達範囲を絞る（Tailscale・ローカル運用はこれで通る） |
| `ALLOW_UNAUTHENTICATED=1` | 承知のうえで無認証のまま公開する |

ループバック・Tailscale帯に絞ってあればパスワード無しでも起動する。§16.1 の互換性は保つ。

### 16.3 JSONボディの上限

**未認証のリクエストに大きなボディをパースさせない。**

| 対象 | 上限 |
|---|---|
| `/api/login`（認証前に body を読む唯一のルート） | 256KB |
| 認証後の通常API | 256KB |
| 取り込み（世界・キャラクターカード・ロアブック） | 20MB |

**1リクエストにJSONパーサを1つだけ通す。** 小さい共通パーサを先に置いてから
大きいパーサを足す形にはできない（先に小さい方が413にしてしまい、後段へ到達しない）。
そこで認証の後ろで**パスを見て上限を選ぶ**1枚のミドルウェアにしてある。

エラーハンドラは**ミドルウェアが付けた status を尊重する**。一律500にすると、
上限超えが「サーバ内部エラー」として画面に出て、設定どおりに拒否したのか
壊れたのかが区別できない。

## 17. 取り込みと書き出し

| 対象 | 形式 |
|---|---|
| 世界一式 | 独自JSON（`character_chat_world`）。往復可能 |
| キャラクター | Character Card V2（`chara_card_v2`）。取り込みも可 |
| ロアブック | V2 `character_book` |
| 会話 | JSON（候補を含む）／テキスト |

**取り込みは1トランザクション。** 途中で失敗したときに、世界だけ・場所だけが残った
半端な状態を作らない（場所IDはグローバル一意なので、半端に残ると同じIDで入れ直せなくなる）。
better-sqlite3 のトランザクションは同期実行なので、この中で `await` しないこと。

**世界の取り込みではIDを振り直し、参照を張り替える。**

- キャラ: 新ULIDを発行し、旧ID→新IDの対応表でメモリーの `subject`・シナリオの参加者を張り替える。
  メモリーの `game_time` は暦ごと持ち出すのでそのまま持ち込める
- 場所: IDはグローバル一意なので、衝突したら `_2` 等の接尾辞を付けてリマップし、
  ロアの場所トリガーとシナリオの初期ステートを追随させる
- エリア: `areas` を持たない古い書き出しでも、**場所が実際に使っているエリアは選択肢に補う**

- 冪等であること。2回実行しても落ちない

## 21. スナップショット（画像生成）

会話の「その瞬間」を絵にする。**明示操作でだけ動き、送る前にプロンプトを確認・修正できる。**
自動生成は行わない（課金が読めず、意図と違う絵が量産されるため）。

### 21.1 何を基準に描くか

**対象メッセージの `state_after`。チャットの現在ステートではない。**
過去のメッセージを選んだとき、当時の場所・天候・時刻で描けるようにするため。
在席者も当時の `state_after.present` から引く（参加キャラ一覧ではない。途中で出入りするので、
その時いなかった人まで描かれてしまう）。

対象は **assistant の `kind = 'normal'` のみ**。user と場面転換マーカーには作れない。

### 21.2 プロンプトの組み立て（`domain/snapshot.ts`）

**ここではLLMを呼ばない。** テンプレートで組んで見せ、直してもらう。
プレビューが課金しないのはこのため。将来 utility model で英訳・タグ化する余地は残す。

| 順 | 内容 |
|---|---|
| 1 | `settings.image_style_prompt`（画風） |
| 2 | 在席キャラの `appearance` |
| 3 | ペルソナの `appearance`（`include_persona` のときだけ。既定OFF） |
| 4 | 場所 / 季節・時刻・日照 / 天候（屋内なら天候は省く） |
| 5 | 対象メッセージの**地の文**（400字まで）。セリフは絵にならないので落とす |
| 6 | 「画面に文字を描かせない」1行（`settings.image_no_text`、既定ON） |

**要素を1行ずつ並べるだけで、見出し（`Characters:` などのラベル）は付けない。**
一度 `Characters:` / `Scene:` / `Composition:` の3節に分けて試したが、
**gpt-image 系では付けない方が良い絵が出た**ので戻してある。
同じことを繰り返し試さないよう、判断の記録としてここに残す。

在席者0人・`appearance` が全員空・地の文なし・参照できる画像なし、はいずれも警告として返し、
プレビュー画面に出す（黙って人物なしの絵を作らない）。

#### 地の文の切り出し

**話者では分けない。`「」` の中身を落とす。**
このアプリのキャラ発話はセリフと地の文が同じ塊に入り、
姿勢・視線・仕草といった**描画に直結する記述はむしろそちらに集中している**。

```
ノア: 「……補修図です。」ノアは腰を屈め、囲みの中を目で数えた。「刻印石三基——」
```

`speaker === 'narrator'` だけを拾うと、この行から拾えるものが何も無くなる。
対象は `user` 以外のすべての発話で、そこから `「」` の中身を除いた残りを繋ぐ。

**切り出しの規則は表示と共有する**（`splitDialogue`、`shared/types.ts`）。
会話画面の `BubbleText` が同じ関数でセリフ（`dlg`）と地の文（`act`）に分ける。
片方だけ直すと「画面には薄く見えているのに絵の指示には入っていない」という
追いにくい食い違いになる。

`utterances` が空のとき（発話パースが効いていない古いメッセージ）だけ本文から拾う。
**`narration || content` にしない。** セリフしか無いターンで本文へ落ちると、
話者ラベルが場面の描写として入り、「地の文がありません」の警告も出なくなる。

#### 文字を描かせない指示

地の文をそのまま渡すため、指示が無いと看板・書類・字幕の形で文字が描き込まれやすい。
`image_no_text`（既定ON）で末尾に1行付ける。**末尾に置くのは、プレビューで
その回だけ消せるようにするため。** 看板の文字を意図して描かせたい世界では設定でOFFにする。

### 21.3 外見（`appearance`）

`characters` と `personas` に持つ。**本文生成のプロンプトには載せない。**
載せると本文側の予算を食ううえ、英語のタグ列が地の文へ漏れる。
`persona`（性格・背景の文章）とは用途が違うので列を分けている。

### 21.4 参照画像

在席キャラ（＋`include_persona` ならペルソナ）の画像を `input_references` として送る。

**参照専用に上げた画像があればそれを、無ければアバターを使う。**
アバターは丸アイコン用に**正方形へ切り抜いて320px**まで落としてあり
（`fileToAvatarDataUrl`）、全身像を上げても顔まわりしか残らない。
服・体型・小物という「絵にしたい情報」が入口で失われるので、参照専用の口を別に持つ。

- **4件までに切る。** 16件受けるモデルもあれば4件のものもあるので低い方に合わせる
- **URLはクライアントから受け取らない。** サーバがDBから組み直す。
  任意のURLを送り込めるようにすると、取得先を指定できる踏み台になる
- 送る相手はプレビューで名前と**出どころ**（参照画像／アバター）を見せる。
  質の落ちるアバターで描かれていることに気づけるようにするため

#### 保存（`reference_images`）

**`characters.avatar` の隣に列を足さない。** `repo/characters.ts` も
`repo/personas.ts` も `SELECT *` で引いているので、数百KBの列を足すと
`GET /worlds/:id/characters`（会話画面が毎回読む）に全キャラぶんの画像が載る。
スナップショットで避けたのと同じ失敗になる。

別テーブルに BLOB で持ち、`repo/references.ts` は `SELECT *` を使わない
（メタと画像で関数を分ける）。持ち主はキャラかペルソナのどちらか一方で、
SQLiteの外部キーは1列で2つのテーブルを指せないため列を分け、CHECK で保証する。
**1人につき1枚**。差し替えは delete → insert を1トランザクションで行い、
**IDが変わる**ので配信を `immutable` にできる。

| メソッド | パス | 中身 |
|---|---|---|
| GET | `/api/characters/:id/reference` | メタ（画像なし）。未設定なら404 |
| PUT | `/api/characters/:id/reference` | `{ data_url }`。既存があれば差し替え |
| DELETE | `/api/characters/:id/reference` | 外す |
| GET | `/api/references/:id/image` | バイナリ配信（`private` ＋ `immutable`） |

ペルソナ側も `/api/personas/:id/...` で同じ3本。

#### 受け取るときの検査

**ここを通ったものをそのまま上流へ送る**ので素通しにしない。

- `data:image/(png|jpeg|webp);base64,` の形であること
- **先頭バイトが宣言した種別と一致すること**（PNG署名 / `FFD8` / `RIFF….WEBP`）。
  宣言だけを信じない
- デコード後 6MB 以下（クライアントは長辺1600pxへ縮めて送るが、APIを直接叩かれても止まる）

ボディ上限は §16.3 の枠組みのまま、**この PUT 2本だけ 10mb** を通す
（通常は 256kb で、300KB前後の参照画像が通らない）。
上限をルート側の6MBより大きく取るのは、**先に body-parser が413にすると
理由の分かるエラーを返せない**ため。

#### クライアント側の縮小

`fileToReferenceDataUrl`（`client/src/components.tsx`）で**長辺1600pxへ縮小、
切り抜かない**。`fileToAvatarDataUrl` とは別関数にしてある。正方形クロップの
有無が本質的な違いなので、共通化すると片方の都合がもう片方へ漏れる。
EXIFの回転は `imageOrientation: 'from-image'` で反映する。

#### 書き出しには含めない

`routes/exports.ts` が出すのはアバターまで。世界の書き出しはJSONなので、
参照画像を含めると数MB〜数十MBになり、取り込みの上限（20mb）にも当たりやすい。

### 21.5 保存と配信

**画像はDBの `snapshots` テーブルに BLOB で持つ**（不変条件 #22「DBは1ファイルで完結する」）。
base64のTEXTだと33%膨らむうえ、JSONに載せない方針なので文字列で持つ意味がない。

**画像データをJSONレスポンスに載せない。** 1枚あたり数百KB〜数MBあるので、
会話の読み込みに混ざると一気に重くなる。リポジトリ層も他と違って `SELECT *` を使わず、
「メタだけ引く」「画像だけ引く」で関数を分けてある。

- 一覧は `GET /chats/:id` の応答に**メタだけ**同梱する。
  メッセージごとのAPIにするとメッセージ数だけ通信が増える（N+1）
- 実体は `GET /api/snapshots/:id/image` でバイナリ配信。
  `Cache-Control: private, max-age=31536000, immutable`
  — **`private` であること**（認証の内側の個人的な内容を共有プロキシに載せない）。
  作成後に中身が変わらないので `immutable` が使える

### 21.6 プロバイダ層（`llm/image.ts`）

OpenRouter の専用 Image API `POST {BASE}/images` を使う（新しい画像モデルはこちらにのみ
追加されている）。PixAI 等へ差し替えられるよう、呼び出し側は関数の形だけを知る。

- `response_format` は送らない（応答は常に `data[].b64_json`）
- `media_type` は省略されることがある。欠けていたら `image/png` として扱う
- `IMAGE_TIMEOUT_MS`（既定 120000）で打ち切る。
  **打ち切っても上流で生成が進んでいれば課金され得る**ので、その旨をエラーに含める
- 画像が無い／0バイトの応答は明示エラー（空を保存しない）

### 21.7 生成ロックとは別枠

**`messages.ts` の `inflight` は使わない。** 画像生成の最中も会話を続けられるべき。
`routes/snapshots.ts` 内の軽いロックで、同じメッセージへの二重生成だけを 409 で弾く。

`settings.image_model` が空なら機能そのものが無効。`GET /api/config` の `imageEnabled` で
画面に伝え、会話画面は入口ごと出さない。**既定を空にするのは、知らないうちに課金させないため。**

### 21.9 サムネイル

原寸は1枚1〜2MBある。チャットとアルバムの一覧にそのまま並べると読み込みが嵩むので、
**縮小版（長辺800px・WebP q0.82）を `snapshots.thumb` に持つ**。
実測で 5.5MB → 1.0MB（画像部分は 5.2MB → 0.6MB）になった。

- `thumb_bytes = 0` は**未作成**。表示側は原寸へ落ちるので、機能としては壊れない
- 種別は原寸と違う（原寸PNG／縮小版WebP）ので `thumb_mime` を別に持つ
- **サーバでは縮小できない。** 画像ライブラリ（ネイティブ依存）を増やしたくないので、
  ブラウザのcanvasで作って `PUT /api/snapshots/:id/thumb` で送る。
  検査は参照画像と同じ `util/imageData.ts` を通す
- 生成直後に作る。**失敗しても生成は成功のまま**（原寸で出るだけなので、
  ここでエラーを見せると「絵は作れているのに失敗したように見える」）
- 800pxにするのは、チャットの表示幅が358pxで高精細画面では2〜3倍要るため
- 一覧では縮小版なので、**タップで原寸を開く逃げ道を必ず置く**
- この機能より前に作った分は、アルバムの「サムネイルを作る（n枚）」でまとめて作る
  （`GET /api/worlds/:id/snapshots/missing-thumbs`）

### 21.8 アルバムと整理（`/album`）

画像はDBに入るので放置すると育つ一方。**枚数と合計サイズを必ず添える**
（どれを消せばどれだけ空くかが分からないと整理の判断ができない）。

| メソッド | パス | 中身 |
|---|---|---|
| GET | `/api/albums` | 世界ごとの枚数と合計バイト数。1枚も無い世界は含めない |
| GET | `/api/worlds/:id/snapshots` | その世界のメタ一覧。会話名と `seq` を添える（画像は含めない） |
| POST | `/api/snapshots/delete` | `{ ids: [] }` を**1トランザクション**で削除し、消えた件数を返す |

`snapshots` は `chat_id` しか持たないので、世界は `chats` との JOIN で解決する
（`idx_snapshots_chat` があるので追加の索引は要らない）。
一括削除を1トランザクションにするのは、途中で失敗して半端に消えた状態を残さないため。

画面は世界の一覧 → その世界のグリッド（**会話ごとの見出し**）。
`loading="lazy"` で近づいたものだけ読む。サムネイル列は持たない（重くなったら次の弾で検討）。

**削除の連鎖。** `PRAGMA foreign_keys = ON` と外部キーで、
メッセージ・会話・世界のいずれを消してもその画像は消える。
外部キーの連鎖は `foreign_keys` が切れた瞬間に黙って壊れる種類の保証なので、
3経路とも回帰テストで固定してある。世界の削除確認には枚数を出す（`worldUsage.snapshots`）。

**fork ではコピーされない。** 分岐は新しいメッセージ行を作るので、
元のメッセージに紐づく画像は分岐先に出ない。必要なら作り直す。

## 付録A. v1.4 からの主な変更

| 項目 | v1.4 | v2 |
|---|---|---|
| 会話の順序 | ULID | `messages.seq` ＋ 一意制約 |
| 再生成の基準 | `chats.state` にフォールバック | `chats.initial_state` |
| イベント判定 | 生成前・同一ターンに注入 | **生成後・次ターンに注入** |
| イベント条件 | 平坦なAND | `all` / `any` / `not` の条件式 |
| イベント | トリガーのみ | ＋ `check` / `chance` / `priority` / `inject_mode` / `set_vars` |
| 進行フラグ | なし | `state.vars` ＋ `vars_schema` |
| エリア | クライアントに固定5種 | 世界ごとに保持（既定8種、表示名は可変） |
| 時間を進める | 手動編集のみ（抽選なし） | ＋「場面を進める」（抽選・イベント判定あり） |

| 発火記録 | 生成のたび | `generation_status = complete` のときのみ |
| Cookie | secure なし | `secure` ＋ `trust proxy` ＋ ログインレート制限 |

## 付録B. 用語

| 用語 | 意味 |

| 基準ステート | 差分を足す前のステート。モードごとに決め方が違う（§4.3） |
