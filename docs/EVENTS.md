## 1. まず有効にする

**進行フラグは既定でOFFです。** 使う前に有効にしてください。

| 場所 | 項目 |
|---|---|
| 設定 → Events & Progress | 「条件付きイベント」（既定ON）／「進行フラグ」（**既定OFF**） |
| 会話の ＋ → この会話の設定 | 継承 / ON / OFF で会話ごとに上書き |

解決順は **会話 → シナリオ → 全体設定** です。会話とシナリオが「継承」なら全体設定が効きます。

> **進行フラグがOFFのままだと、`var` を使った条件は常に偽になります。**
> 「条件は合っているのに一度も発火しない」の最も多い原因です。

## 2. 全体像

フェーズとイベントは、こういう関係で回ります。

```
        ┌─────────────────────────────────────┐
        │  進行フラグ  case_phase = 1         │  ← 世界が持つ状態
        └───────────────┬─────────────────────┘
                        │ when で参照
                        ▼
        ┌─────────────────────────────────────┐
        │  イベント「名簿の存在を知る」        │
        │  when: case_phase == 1 かつ 古書店   │
        │  set_vars: case_phase → 2           │
        └───────────────┬─────────────────────┘
                        │ 発火すると
                        ▼
        ┌─────────────────────────────────────┐
        │  case_phase = 2 に進む               │  ← 次のイベントの条件が開く
        │  「進行状況」ブロックの記述も変わる   │
        └─────────────────────────────────────┘
```

**フェーズは「今どの段階か」、イベントは「次の段階へ進む扉」**です。
フェーズだけ作っても物語は進みません。**各フェーズへ進むイベントを必ず1つ以上用意してください。**

### 判定と注入のタイミング

```
あなたが送信
   ↓
AIが応答を書く（この時点ではイベントは効いていない）
   ↓
応答が完了 → 時刻・場所が確定 → ★ここで判定
   ↓
発火したら set_vars を適用して記録
   ↓
次のターンのプロンプトに「発生中の出来事」として載る
```

**注入は次のターンです。** 「カフェに着いた」応答の直後に判定し、
「店内は混んでいる」は次のターンから効きます。
途中で停止した応答では判定しません（次のターンで改めて判定されます）。

## 3. 進行フラグを定義する

**世界 → 世界の編集 → 「進行フラグの定義」** にJSON配列を書きます。
**ここに書いたキーしか使えません**（誤字による野良キーの増殖を防ぐため）。

### 3.1 フィールド

| フィールド | 必須 | 意味 |
|---|---|---|
| `key` | ● | 識別子。英字始まりの英数字と `_`。**作成後は変えない** |
| `type` | ● | `"number"` / `"boolean"` / `"string"`（string は32文字まで） |
| `role` | | `"phase"`（段階）／ `"flag"`（省略時） |
| `default` | | 初期値。省略時は 0 / false / 空文字 |
| `label` | | 画面とプロンプトに出す名前 |
| `min` `max` | | 数値の範囲。外れた値は丸める |
| `monotonic` | | `true` なら**後退する更新を捨てる**（フェーズは基本 true） |
| `update_mode` | | `"system_only"` / `"system_and_llm"`（省略時） |
| `phases` | | `role: "phase"` のときの各段階 |

### 3.2 `phases` の中身

| フィールド | 意味 |
|---|---|
| `value` | 数値 |
| `name` | 段階の名前 |
| `public_state` | **プロンプトに載る**。その段階でAIに知らせてよい状況 |
| `private_note` | **プロンプトに絶対に載らない**。あなた用のメモ |

### 3.3 `phase` と `flag` の使い分け

| | `role: "phase"` | `role: "flag"`（省略時） |
|---|---|---|
| 想定 | 一本道で進む段階 | 個別の到達・関係値 |
| プロンプトへの出方 | 段階名＋`public_state` の文章 | `key = 値（ラベル）` の1行 |
| 例 | 事件の進行、章 | 「トビーと会った」「信頼度7」 |

**フェーズは1つの物語につき1本**にしてください。2本以上あると条件が組み合わせ爆発します。

### 3.4 `update_mode` の選び方

| | 誰が書けるか | 向いている用途 |
|---|---|---|
| `system_and_llm`（既定） | AI・イベント・手動 | 「会った」「信頼度」など、AIが自然に判断できるもの |
| `system_only` | イベント・手動のみ | **フェーズ**。AIに勝手に進められると構成が壊れる |

`system_only` にすると、AI向けの「進行状況の更新」指示文からもそのキーが除外されます。
AIが `set_var: case_phase=3` と書いても破棄され、警告が返ります。

### 3.5 記入例

```json
[
  {
    "key": "case_phase",
    "type": "number",
    "role": "phase",
    "default": 0,
    "label": "灰の名簿・事件の進行",
    "min": 0,
    "max": 4,
    "monotonic": true,
    "update_mode": "system_only",
    "phases": [
      {
        "value": 0,
        "name": "日常",
        "public_state": "街は平穏。名簿の件はまだ誰も口にしていない。",
        "private_note": "ここで焦って伏線を出さない。日常の描写を優先する"
      },
      {
        "value": 1,
        "name": "違和感",
        "public_state": "保安庁の動きが慌ただしいという噂が流れている。"
      },
      {
        "value": 2,
        "name": "名簿の存在",
        "public_state": "『灰の名簿』と呼ばれる記録の存在が話題に上っている。"
      },
      {
        "value": 3,
        "name": "追跡",
        "public_state": "名簿を巡って複数の人物が動いている。緊張が高い。"
      },
      {
        "value": 4,
        "name": "決着",
        "public_state": "名簿の行方に決着がついた。"
      }
    ]
  },
  { "key": "toby_met", "type": "boolean", "default": false, "label": "トビーと接触済み" },
  { "key": "henry_trust", "type": "number", "default": 0, "label": "ヘンリーの信頼度", "min": 0, "max": 10 }
]
```

> **JSONは1文字違うと保存できません。** 保存時に
> 「保存できません: Unexpected token …」と出たら、次の3つを疑ってください。
> ① 括弧の対応（`[` `]` と `{` `}`）／② 最後の要素の後ろの余計なカンマ／
> ③ 全角の引用符（`”`）が混じっている。

## 4. イベントの項目

**世界 → イベント → エントリを開く**で編集します。

| 項目 | 既定 | 意味 |
|---|---|---|
| `title` | 新しいイベント | 管理用。プロンプトには載らない |
| `kind` | `ambient` | 分類。`ambient`（雰囲気）／`story`（物語）／`critical`（必須）。**判定には影響しない**、整理用 |
| `when` | `{}` | 条件式。**空なら常に真** |
| `check` | `every_turn` | いつ判定するか |
| `chance` | `1` | 0.0〜1.0。範囲外は丸める |
| `trigger` | `once` | 何回起きるか |
| `trigger_var` | 空 | `once_per_phase` で見るキー |
| `cooldown_days` | `0` | `cooldown` のときのゲーム内日数 |
| `priority` | `0` | 大きいほど先に採用される |
| `inject_mode` | `fact` | `fact`（事実）／`instruction`（演出指示） |
| `inject` | 空 | **プロンプトに載る一文**。ここが本体 |
| `set_vars` | `[]` | 発火時に進行フラグを書き換える |
| `enabled` | `1` | OFFにすると判定されない |

## 5. 条件式 `when` の書き方

### 5.1 基本の3つの規則

```json
{ "month": 9, "weather": "雨" }
```
**同じ階層に並べた項目は AND。** 「9月 かつ 雨」。

```json
{ "weather": ["雨", "雪", "みぞれ"] }
```
**配列で並べた値は OR。** 「雨 または 雪 または みぞれ」。

```
{ "all": [ … ], "any": [ … ], "not": { … } }
```
**入れ子は `all` / `any` / `not`。**

### 5.2 述語の一覧

| 述語 | 型 | 例 | 備考 |
|---|---|---|---|
| `season` | 文字列／配列 | `"秋"` | |
| `month` | 数値／配列 | `9` または `[9, 10]` | |
| `week` | 数値／配列 | `4` | 月内の第1〜4週 |
| `weekday` | 文字列／配列 | `"土"` | |
| `time_after` | `"HH:MM"` | `"17:00"` | **その時刻を含む**（17:00 は真） |
| `time_before` | `"HH:MM"` | `"23:00"` | **その時刻を含まない**（23:00 は偽） |
| `location` | 文字列／配列 | `"vein_bookstore"` | 場所ID |
| `location_area` | 文字列／配列 | `"harbor"` | **エリアID**（表示名ではない） |
| `weather` | 文字列／配列 | `"霧"` | |
| `present_has` | 文字列／配列 | `"01JQ..."` | **全員いる**とき真 |
| `present_lacks` | 文字列／配列 | `"01JQ..."` | **1人でもいたら**偽 |
| `var` + 比較子 | | `{"var": "case_phase", "gte": 2}` | |

`var` の比較子は `eq` / `ne` / `in` / `gt` / `gte` / `lt` / `lte`。
**比較子を書かないと「値が真であること」の判定**になります（boolean 向け）。

| 書き方 | 意味 |
|---|---|
| `{ "var": "toby_met" }` | `toby_met` が true |
| `{ "var": "toby_met", "eq": false }` | `toby_met` が false |
| `{ "var": "case_phase", "in": [2, 3] }` | フェーズが 2 か 3 |

> **JSONに `//` のコメントは書けません。** メモを残したいときは、
> 進行フラグの `private_note` か、イベントの `title` を使ってください。

### 5.3 実例

**秋の夕方、雨か雪の日に、港で**

```json
{
  "all": [
    { "season": "秋" },
    { "time_after": "16:00", "time_before": "19:00" },
    { "weather": ["雨", "雪"] },
    { "location_area": "harbor" }
  ]
}
```

**フェーズ2以上で、トビーがその場にいないとき**

```json
{
  "all": [
    { "var": "case_phase", "gte": 2 },
    { "not": { "present_has": "01JQ8FTOBYXXXXXXXXXXXXXXXX" } }
  ]
}
```

**古書店にいるか、または夜の裏通りにいる**

```json
{
  "any": [
    { "location": "vein_bookstore" },
    { "all": [{ "location_area": "backstreet" }, { "time_after": "21:00" }] }
  ]
}
```

**深夜（22:00〜翌02:00）** — ここは要注意です

```json
{ "any": [{ "time_after": "22:00" }, { "time_before": "02:00" }] }
```

`{ "time_after": "22:00", "time_before": "02:00" }` と書くと
「22時以降 かつ 2時より前」となり、**絶対に成立しません**。日を跨ぐ時間帯は `any` を使ってください。

### 5.4 条件なし

`{}` は常に真です。`check` と `trigger` だけで制御したいときに使います。

```json
{}
```

## 6. `check`：いつ判定するか

| 値 | 動作 | 向いている用途 |
|---|---|---|
| `every_turn` | 条件を満たす限り毎ターン判定 | 天候・時間帯の雰囲気 |
| `on_enter` | **前ターンは偽、今ターンは真**のときだけ | 入店・初対面・フェーズに入った瞬間 |
| `on_day_change` | 日付が変わったターンだけ | 朝の日課、日替わりの噂 |
| `on_location_change` | 場所が変わったターンだけ | 到着時の描写 |

### `on_enter` の考え方

「状態が切り替わった瞬間」を捉えます。条件が続いている間は再発火しません。

```
ターン1: 中央にいる       → 条件 偽
ターン2: 港へ移動         → 条件 真  ★ここで発火
ターン3: まだ港にいる     → 条件 真だが、前ターンも真なので発火しない
ターン4: 中央へ戻る       → 条件 偽
ターン5: また港へ         → 条件 真  ★また発火（trigger が許せば）
```

`trigger: "repeat"` と組み合わせると「港に来るたび1回」になります。

## 7. `trigger`：何回起きるか

| 値 | 「同じ〇〇」では1回だけ | 補足 |
|---|---|---|
| `once` | その会話で1回 | 物語上の一度きりの出来事 |
| `once_per_day` | ゲーム内の同じ日 | 日課 |
| `once_per_visit` | 同じ場所に滞在している間 | 到着時の描写 |
| `once_per_phase` | 指定フラグの値が同じ間 | **`trigger_var` の指定が必須** |
| `once_per_year` | ゲーム内の同じ年 | 年中行事 |
| `cooldown` | 前回から `cooldown_days` 日 | 定期的な噂 |
| `repeat` | 制限なし（履歴を見ない） | 常時の雰囲気 |

発火の記録は**会話ごと**です。別の会話では改めて発火します。

### `once_per_phase` の使いどころ

```json
{ "trigger": "once_per_phase", "trigger_var": "case_phase" }
```

`case_phase` が 1 の間は1回だけ。2 に進むとまた1回発火できます。
**フェーズを進めるイベントには基本これを使ってください。** `once` だと、
再生成やフォークで状況が変わったときに二度と発火しなくなります。

> `trigger_var` を空のままにすると発火しません（評価結果に
> 「trigger_var が未設定または未定義」と出ます）。

## 8. `chance`：確率イベント

`0.0`〜`1.0`。`1` なら必ず、`0.3` なら3割です。

### シードは固定されています

抽選のたびに乱数を引くのではなく、**チャットID・イベントID・スコープから決まる固定値**を使います。

- **再生成しても結果は変わりません。** 「当たるまで作り直す」ができないようにするためです
- スコープを持つ trigger（`once_per_day` など）では、**その日ごとに**結果が決まります
- 天候も同じ仕組みで、同じ日なら再生成しても同じ天気になります

### 使い分けの目安

| 用途 | `chance` | `trigger` |
|---|---|---|
| 街の雰囲気（たまに出る） | 0.2〜0.4 | `repeat` |
| 日替わりの小さな出来事 | 0.5 | `once_per_day` |
| 物語の分岐点 | **1** | `once_per_phase` |

**物語を進める `critical` なイベントに確率を使わないでください。** 進まなくなります。

## 9. `inject_mode`：事実か、演出指示か

`inject` に書いた文が、プロンプトのどこに置かれるかが変わります。

```
# 現在の状況        ← 時刻・場所・天候
# 進行状況          ← フェーズの public_state
# 発生中の出来事    ← inject_mode: "fact"
# 今回の演出指示    ← inject_mode: "instruction"
```

後ろほど強く効きます。

### `fact`（事実）

「そういう状況である」と伝えるだけ。**AIがどう扱うかは任せます。**

```
中央広場に夜市が出ている。屋台の灯りが遠くに見える。
```

### `instruction`（演出指示）

「こう書け」と指示します。**1ターンに1件までしか採用されません。**

```
この場面のどこかで、積荷の陰からトビーを登場させること。
アシュリーは彼に気づいても、すぐには声をかけない。
```

### 書き分けの指針

| | `fact` | `instruction` |
|---|---|---|
| 使う場面 | 世界の状態が変わった | 特定の展開を起こしたい |
| 書き方 | 情景・事実の文 | 命令形 |
| 使いすぎると | 無視されやすい | 文章が指示の消化になる |

**基本は `fact`**、どうしても起こしたい展開だけ `instruction` にしてください。

## 10. `set_vars`：フェーズを進める

発火と同時に進行フラグを書き換えます。**物語を次の段階へ進めるのはこの仕組みだけです。**

```json
[{ "key": "case_phase", "op": "set", "value": 2 }]
```

| `op` | 動作 |
|---|---|
| `set` | 代入 |
| `add` | 加算（**数値のみ**） |

複数まとめて書けます。

```json
[
  { "key": "case_phase", "op": "set", "value": 2 },
  { "key": "toby_met", "op": "set", "value": true },
  { "key": "henry_trust", "op": "add", "value": 1 }
]
```

### 権限

**`update_mode: "system_only"` のキーも、イベント経由なら書き換えられます。**
これがフェーズを `system_only` にできる理由です — AIには触らせず、あなたが設計したイベントでだけ進めます。

ただし `monotonic: true` のキーは**後退できません**。

```json
[{ "key": "case_phase", "op": "set", "value": 1 }]
```
現在 `case_phase` が 2 なら、この操作は棄却されて警告が出ます。

## 11. 優先度と1ターンの上限

1ターンに採用されるのは **`priority` の大きい順に `event_max_per_turn` 件**（既定2件）です。
同じ優先度ならID順になります。

**`instruction` は上限とは別に、常に1件までです。**

### 優先度の目安

| 種類 | `priority` |
|---|---|
| フェーズを進める（`critical`） | 100 |
| 物語上の出来事（`story`） | 50 |
| 雰囲気（`ambient`） | 0 |

イベントが増えてくると、優先度の低いものが押し出されます。
評価結果に `capped`（上限超過）が並ぶようなら、設定 → Events & Progress の
「1ターンのイベント上限」を上げてください（最大5件）。

## 12. 完全な設計例

「灰の名簿」を、フェーズ0→4で進める一式です。そのままコピーして使えます。

### 12.1 進行フラグの定義

**世界 → 世界の編集 → 進行フラグの定義**

```json
[
  {
    "key": "case_phase",
    "type": "number",
    "role": "phase",
    "default": 0,
    "label": "灰の名簿・事件の進行",
    "min": 0,
    "max": 4,
    "monotonic": true,
    "update_mode": "system_only",
    "phases": [
      { "value": 0, "name": "日常",
        "public_state": "街は平穏。名簿の件はまだ誰も口にしていない。",
        "private_note": "焦って伏線を出さない。日常の描写を厚く" },
      { "value": 1, "name": "違和感",
        "public_state": "保安庁の動きが慌ただしいという噂が流れている。",
        "private_note": "まだ名簿という言葉は出さない" },
      { "value": 2, "name": "名簿の存在",
        "public_state": "『灰の名簿』と呼ばれる記録の存在が話題に上っている。" },
```

## 13. デバッグ手順

イベントが思ったとおりに動かないときは、この順で確認します。

### 手順1: 有効になっているか

設定 → Events & Progress で「条件付きイベント」と「進行フラグ」がON。
会話の ＋ → この会話の設定 が OFF になっていないか。

### 手順2: 評価する

**世界 → イベント → 「最新のチャットで評価」**

各イベントが**どの段階で落ちたか**が出ます。

| 結果 | 意味 | 次に見るところ |
|---|---|---|
| `採用` | 発火する | — |
| `条件不一致` | `when` を満たしていない | 手順3へ |
| `タイミング外` | `check` に合わない | `on_enter` なら前ターンも真になっていないか |
| `発火済み` | 同じスコープで既に発火した | 発火履歴を消す（手順5） |
| `抽選外れ` | `chance` を外した | 詳細に実際の乱数値が出ます |
| `上限超過` | 優先度で押し出された | `priority` を上げるか上限を増やす |

### 手順3: 条件を分解する

条件不一致のときは、`when` を一時的に空 `{}` にして発火するか見ます。
発火するなら条件側の問題です。1つずつ足して、どれが偽になるか特定してください。

よく間違えるのは以下です。

- **エリアは表示名ではなくID。** 「港」ではなく `harbor`
- **キャラはIDが必要。** 名前では判定できません
- 場所メモ（「路地裏」など未登録地）を使っている間は `location` / `location_area` が常に偽
- 進行フラグがOFFだと `var` が常に偽

イベント編集画面の条件欄の下に、**その世界で使えるエリアIDの一覧**が出ています。

### 手順4: プロンプトを見る

**会話の ＋ → プロンプトを確認**

- 「イベント判定」に各イベントの結果が並びます
- 「現在の状況」に `# 発生中の出来事` / `# 今回の演出指示` が入っているか確認します
- **発火したターンにはまだ載りません。次のターンから載ります**

### 手順5: 発火履歴を消す

**会話の ⋯ → ステート編集 → 発火履歴**

`once` などで一度発火してしまうと再発火しません。テスト中は履歴を1件ずつ消せます。

### 手順6: フェーズを直接動かす

**会話の ⋯ → ステート編集**

進行フラグを直接編集できます。**手動編集だけは `monotonic` と `system_only` を無視します**ので、
フェーズを戻して繰り返しテストできます。

## 14. よくある失敗

エラーにならず**静かに発火しない**ものが大半です。

| 症状 | 原因 | 対処 |
|---|---|---|
| `var` の条件が一度も通らない | 進行フラグがOFF | 設定でONにする |
| エリア条件が通らない | 表示名を書いている | エリアID（`harbor` 等）を書く |
| 場所条件が通らない | 場所メモを使っている | 場所を登録するか、条件から外す |
| 深夜の条件が通らない | `time_after` と `time_before` をANDにしている | `any` で囲む |
| `once_per_phase` が発火しない | `trigger_var` が空 | フラグのキーを指定する |
| フェーズが進まない | `set_vars` を書いていない | 進める `set_vars` を足す |
| フェーズが進まない | AIに `set_var` を書かせようとしている | `system_only` のキーはイベントからのみ |
| フェーズが戻らない | `monotonic: true` | 仕様どおり。戻すならステート編集から |
| 発火したのに描写に出ない | 発火ターンではなく次ターンに載る | 1ターン待つ |
| 一部のイベントだけ出ない | 1ターンの上限（既定2件） | `priority` を上げるか上限を増やす |
| `instruction` が2つ出ない | 演出指示は常に1件まで | 片方を `fact` にする |
| 一度発火して二度と出ない | `trigger: once` | `once_per_phase` などに変える |
| 再生成しても抽選結果が同じ | 仕様（シード固定） | `chance: 1` にするか条件を変える |
| 保存できない | JSONの構文エラー | 括弧とカンマの対応を確認 |
| フェーズ遷移の警告が消えない | `op: "add"` で進めている | 到達判定は `op: "set"` のみ数える |

### 特に注意: `add` はフェーズ遷移として数えられません

フェーズ遷移の欠落チェックは **`op: "set"` で、その値と一致するもの**だけを数えます。

| 書き方 | 遷移として数えられるか |
|---|---|
| `[{ "key": "case_phase", "op": "add", "value": 1 }]` | ✗ 警告が消えない |
| `[{ "key": "case_phase", "op": "set", "value": 2 }]` | ✓ 数えられる |

動作としては `add` でも進みますが、**どのフェーズへ進むのかが宣言されない**ため、
設計の抜けを検出できません。フェーズは `set` で書いてください。

## 15. 早見表

### イベントの項目

```
title         管理用の名前
kind          ambient | story | critical         （整理用。判定には無関係）
when          条件式（空 = 常に真）
check         every_turn | on_enter | on_day_change | on_location_change
chance        0.0 〜 1.0
trigger       once | once_per_day | once_per_visit | once_per_phase
              | once_per_year | cooldown | repeat
trigger_var   once_per_phase で見るキー
cooldown_days cooldown のゲーム内日数
priority      大きいほど先に採用
inject_mode   fact | instruction
inject        プロンプトに載る一文
set_vars      [{ key, op: "set"|"add", value }]
enabled       0 | 1
```

### 述語

```
season month week weekday
time_after time_before          "HH:MM"（after は含む / before は含まない）
location location_area          ID で指定
weather
present_has present_lacks       キャラID
var + eq|ne|in|gt|gte|lt|lte
all any not                     入れ子
```

### 進行フラグ

```
key type role default label min max monotonic update_mode phases
type        number | boolean | string(32文字)
role        phase | flag
update_mode system_only | system_and_llm
phases      [{ value, name, public_state, private_note }]
            public_state  → プロンプトに載る
            private_note  → 絶対に載らない
```

### 判定の順序

```
1. 有効か        enabled と events_enabled
2. when          条件式
3. check         判定タイミング
4. trigger       同じスコープで発火済みでないか
5. chance        シード固定の抽選
6. 上限          priority 順に event_max_per_turn 件（instruction は1件）
      ↓
   set_vars を適用して記録 → 次のターンのプロンプトへ
```
